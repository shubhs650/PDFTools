# ADR-018: M4 — Comment transfer (import from PDF or JSON, copy/paste between documents)

- **Status:** Proposed. **Scope accepted by the owner on 2026-09-29** (decisions 1, 4–8). The
  technical route (decisions 2–3) is settled by the M4-19 spike, which fills in **Outcome** and
  **Evidence**; ARCHITECTURE.md is amended (decision 9) only after this ADR is accepted.
- **Date:** 2026-09-29
- **Deciders:** Owner (scope); recorded by the coding agent
- **Related decisions:** D-03, D-06, D-15, D-16, D-19 (ARCHITECTURE.md §2); §7.1, §7.6, §13, §14;

- **Related spike / milestone:** M4-19 (spike), M4-20, M4-21

## Context

In EPC document control, comments made on one revision of a document (Rev A) are routinely carried
to the next revision (Rev B) so that the reviewer can check whether each one was addressed.
PDF-XChange Editor has a dedicated **Import** button in Comment → Manage Comments for this, and
lets comments be copied and pasted from the Comments pane; Acrobat has "Import Comments".

ARCHITECTURE.md Rev 0.4 has only the **export** half:

- §7.6: "Annotations | own serializer → CSV / XLSX / JSON";
- §13 M4: "… annotation export";
- §14 Rev 1: "CRS round-trip import + custom column templates" (a different feature: reading a
  filled-in CRS spreadsheet back, not transferring PDF comments).

The owner asked (2026-09-29, M4 plan review) for three routes in M4:

1. **Import comments from another PDF** (e.g. the older revision) into the active document;
2. **Import comments from our own JSON** (the M4-08 export format);
3. **Copy/paste comments** from the Comments pane and the page, within a document and between open
   tabs.

Constraints: annotations stay standard PDF objects with appearance streams that round-trip with
Acrobat Reader and PDF-XChange (D-03, rule 6); no custom appearance-stream generation (ADR-001 B7);
Ctrl+S stays one narrow incremental revision (ADR-005, rule 7); no parsing or file building on the
main thread (rule 1); permissions are honoured in both documents (D-19, rule 9); one undo step per
user action (§7.1).

What PDFium and EmbedPDF 2.15.1 offer today: PDFium has **no API that copies an annotation between
documents** (`FPDF_ImportPages` copies whole pages). EmbedPDF's `createAnnotation` makes a new
annotation from its model, and PDFium then generates the appearance for the types it knows.
Our own object layer (M3-03: reader, serializer, staged patches merged into the Ctrl+S tail;
M3-04: decryption and encryption) can read any object from the source file, including appearance
streams and their resources, but today it only patches existing objects (measurement keys, `/VP`)
and cannot yet add new objects that the Render worker's PDFium instance knows about.

## Options considered

1. **Object copy.** Deep-copy each annotation dictionary from the source with everything it
   references (`/AP` streams and their resources, fonts and images, `/Popup`, reply chain via
   `/IRT`, measurement `/Measure`), renumbered, re-encrypted for the target if needed, written as an
   incremental update on top of the current revision; the Render worker then **reopens original +
   tail** (the M4-Q1 route) so PDFium, the annotation store and the tiles see them.
   - For: exact appearance for every type, including stamps, measurements, other viewers' custom
     appearances and types EmbedPDF cannot author; nothing is lost.
   - Against: the reopen costs time on large files; the imported tail must join the next Ctrl+S
     correctly (it sits between the original and PDFium's own incremental save) and pass the
     ADR-005 verification; the object layer must learn to add objects and extend a page's
     `/Annots`.
2. **Re-create through EmbedPDF.** Read the source's annotations as EmbedPDF models (Work worker)
   and call `createAnnotation` in the target, then stage extra keys (`/Measure`, `/IT`, `/NM`,
   `/T`, dates) through object-layer patches.
   - For: fits the existing path exactly (plugin store, `plugin-history` undo, narrow Ctrl+S, no
     reload).
   - Against: appearances are regenerated by PDFium, so custom appearances from other viewers change
     look; image stamps need their image re-extracted; types EmbedPDF cannot author are dropped.
3. **Hybrid.** Option 1 for PDF → PDF import and copy/paste (the source has real objects), option 2
   for JSON import (JSON carries no appearance streams, so it must be re-created in any case).

## Decision

1. _(Owner, accepted 2026-09-29)_ **Add comment transfer to M4** as three routes: Import Comments
   from a PDF, Import Comments from our JSON (format v1), and Copy/Paste Comments (Comments pane
   and page, within a document and between open tabs). New commands `comment.importComments`
   (Comment → Manage Comments), `comment.copyComments`, `comment.pasteComments` (Ctrl+C / Ctrl+V
   when comments are selected; text selection keeps Ctrl+C for text).
2. _(Proposed, decided by M4-19)_ **Route:** option 3 (hybrid) — object copy for PDF sources and
   copy/paste, re-creation for JSON. If the spike shows object copy cannot meet the save,
   verification or timing criteria, option 2 is used everywhere and the ADR records what is lost.
3. _(Proposed, decided by M4-19)_ **Where the work runs:** reading and deep-copying in the **Work
   worker** (it already holds a read-only copy of each open document; a PDF picked only for import
   is opened there without a tab); the Render worker only applies the result (reopen or
   `createAnnotation`). The main thread sends ids and options and receives counts (rule 1).
4. _(Owner, accepted)_ **Import options:** page range; author, type and status filters; with or
   without replies. **Page mapping:** same page number by default, or with an offset; comments whose
   target page does not exist are listed and skipped. **Placement:** same coordinates when the page
   boxes match; otherwise the same position relative to the crop box, following `/Rotate`.
   **Duplicates:** an annotation whose `/NM` already exists in the target is skipped (so importing
   twice does no harm).
5. _(Owner, accepted)_ **Identity and authorship:** imported comments keep their author (`/T`),
   dates, subject, replies and review states; `/NM` is kept on import (decision 4) and **new `/NM`s
   are assigned on paste** (a paste into the same document would otherwise duplicate ids). Reply
   chains and grouped measurement labels (`/IRT`, `/RT /Group`) stay together and are remapped.
6. _(Owner, accepted)_ **Undo and save:** each import or paste is **one undo step**; the result
   saves with the normal narrow Ctrl+S (rule 7); recovery covers it (ADR-001 B11).
7. _(Owner, accepted; M4-Q2)_ **Permissions:** the target needs **annotate**; the source needs
   **copy** (comment text is content). Encrypted sources are read with their password through the
   M3-04 handler; encrypted targets get the copied strings and streams re-encrypted with the
   target's key.
8. _(Owner, accepted)_ **Clipboard:** in-app only (a per-session store holding the copied
   comments), never the system clipboard. The store holds a self-contained copy, so a paste still
   works after the source tab is closed; it is emptied when the app closes.
9. **Proposed ARCHITECTURE.md wording** (applied only after acceptance):
   - §7.1, new bullet after "Comments pane": "**Comment transfer:** import comments from another
     PDF (e.g. an earlier revision; page range, filters, page mapping, duplicates skipped by `/NM`)
     or from our JSON export, and copy/paste comments between documents; imported comments are
     standard annotation objects saved by the next Ctrl+S (ADR-018)."
   - §7.6, the Annotations row: "own serializer → CSV / XLSX / JSON (JSON also imports, §7.1)".
   - §13 M4: "… redaction with verification, annotation export **and comment transfer (import,
     copy/paste)**."
   - §14 is unchanged (CRS round-trip import stays Rev 1). XFDF/FDF import and export stay out of
     Rev 0 (a Rev 1 candidate).

## Consequences

- **M4 plan:** new tasks M4-19 (spike), M4-20 (Import Comments from PDF and JSON), M4-21
  (Copy/paste comments); the acceptance task becomes M4-22 and gains interop checks for
  transferred comments. M4-08's JSON v1 schema must carry everything needed to re-create each
  annotation (geometry, vertices, quad points, ink paths, line endings, border and cloud style,
  fonts and colours, `/Measure`, image-stamp image as an optional PNG data URI), because JSON
  becomes a round-trip format; the schema is frozen as v1 once M4-20 ships.
- **Object layer:** learns to add new objects and extend a page's `/Annots` (option 1), with
  qpdf cross-checks as in M3-03.
- **Save/verify:** ADR-005's verification must cover imported annotations (compare the target's
  annotation set after save with the Render worker's state).
- **Interop:** the M4 pack adds Rev A → Rev B transfers of Acrobat- and PDF-XChange-made comments,
  checked in both viewers.
- **Not solved here:** telling the reviewer whether a carried-over comment still points at the
  right content in the new revision. That is revision compare, **parked** (§14, rule 14).
- **Risks:** reopen time on 2,000-page targets (measured in M4-19); appearance resources that
  reference objects shared with page content (fonts) are copied, which can grow the file; other
  viewers' private keys inside annotation dictionaries are copied as they are (we never add our own,
  rule 6).
