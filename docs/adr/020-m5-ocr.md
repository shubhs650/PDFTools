# ADR-020: S17 — OCR with the Tesseract WASM core, text layer by our object layer

- **Status:** Proposed (owner to accept). The owner asked for OCR on 2026-10-03 (a user request);
  it is Rev 1 item 1 in ARCHITECTURE.md §14. Code is built under this ADR; ARCHITECTURE.md is
  amended only once it is accepted (CLAUDE.md "Session protocol").
- **Date:** 2026-10-03
- **Deciders:** Owner; recorded by the coding agent
- **Related decisions:** D-08 (search), D-10, D-12 (licenses), D-17 (precache), D-19 (permissions),
  D-22 (no network) (ARCHITECTURE.md §1.5, §3.1, §3.2, §6, §7.7, §9, §10, §14); ADR-002, ADR-004,
  ADR-005, ADR-013, ADR-016, ADR-018; CLAUDE.md rules 1, 2, 4, 5, 7, 9, 10, 11
- **Related spike / milestone:** S17 (`spikes/s17-ocr/`), M5 (`docs/plan/M5.md`)
- **Outcome (spikes only):** **Works with workaround.** The Tesseract WASM core recognizes a
  300 dpi A4 page in about a second in a worker under the verbatim CSP with zero network use;
  the text layer is written by our own object layer, not by PDFium's content generator, which
  rewrites the page's content streams.

## Context

§1.5 lists OCR as a Rev 0 non-goal and §14 as Rev 1 item 1: "OCR (scanned docs, search in
scans, scanned tables)". §14 also reserves the extension point "OCR text layer can be injected
per page into the Work worker's text index". Rev 0 (M1–M4) is complete on the agent side
(docs/PROGRESS.md), and a user asked for OCR. The owner researched the options and found that
Tesseract runs as WebAssembly (tesseract.js), and asked for a plan, a verification and the
implementation.

Constraints that shape the design: everything offline and same-origin (rule 4, §10.1 CSP with
`script-src 'self' 'wasm-unsafe-eval'`, COOP/COEP), permissive licenses only (rule 5), no PDF
work on the main thread (rule 1), every long job cancellable with progress (rule 2), Ctrl+S
stays an incremental narrow tail (rule 7, ADR-005), permission flags honored (rule 9), and the
result must be a standard PDF: invisible text that Acrobat Reader and PDF-XChange search and
select like their own OCR output.

## Options considered

1. **tesseract.js as published** (its `createWorker`/scheduler API). Pros: documented API, image
   decoding, caching. Cons: defaults to jsDelivr for the worker script, the core and the language
   data (`workerPath`, `corePath`, `langPath` all CDN unless overridden), spawns its own
   `blob:` worker from the main thread, caches language data in IndexedDB, depends on
   `node-fetch`, `is-url`, `bmp-js`, `idb-keyval`, `regenerator-runtime`, `zlibjs`; its worker
   is a classic script loaded by `importScripts`. Everything the architecture forbids or does
   not need.
2. **tesseract.js-core directly in our own worker** (the emscripten module tesseract.js itself
   runs). Pros: one dependency (Apache-2.0, no sub-dependencies), our typed RPC, our cancel and
   memory policy, explicit same-origin URLs, SIMD + LSTM-only build only (2.9 MB WASM). Cons:
   its API surface is embind (`TessBaseAPI`, `ResultIterator`) with no typings; we type what we
   use. **Chosen.**
3. **Where the text layer is written.**
   - **A. PDFium text objects** (`FPDFPageObj_CreateTextObj`, `FPDFText_SetText`, render mode 3,
     `FPDFPage_InsertObject`, `FPDFPage_GenerateContent`), then the normal save. Measured: it
     works, but `FPDFPage_GenerateContent` **regenerates every content stream of the page**
     from PDFium's parsed objects: the original streams are orphaned (page 2's two streams
     became one new stream), marked content and optional-content membership would be lost,
     the output is uncompressed, and PDFium adds **one font resource name per text object**
     (89 names for 89 words). Tail: 187 KB for three pages.
   - **B. Our object layer** (the comment-transfer route of ADR-018): per page one new content
     stream with the words as invisible text, appended to `/Contents` behind a `q` … `Q` wrap
     of the original streams, one Helvetica/WinAnsi font added to the page's resources, applied
     by the Render worker as objects (reopen, one undo step, narrow verified Ctrl+S). Measured:
     original streams byte for byte as they were, 13 KB tail for three pages, qpdf clean,
     pixels identical. **Chosen.**
4. **Where the raster comes from.** The Render worker is the scroll path (ADR-004: one call at a
   time), so the **Work worker** renders the page for OCR (as `print.ts` already does), from the
   document as it is now (unsaved changes as its live section). Chosen.
5. **A dedicated OCR worker vs. Tesseract inside the Work worker.** Tesseract's WASM memory grows
   with the page (about 50 MB measured for an A4 page) and `Recognize` is one synchronous call
   of about a second: a mid-page cancel can only be a `terminate()`. A dedicated worker makes
   that cheap and keeps the Work worker's PDFium + Oxide heap out of it. Chosen.

## Decision

1. **Engine:** `tesseract.js-core` 7.0.0 (Apache-2.0; Tesseract 5.1.0, Leptonica BSD-2) used
   directly in a new **OCR worker** (`src/workers/ocr.worker.ts`) behind the typed RPC. Only
   the `tesseract-core-simd-lstm` build ships (every supported browser has WASM SIMD; the legacy
   engine and the relaxed-SIMD variant are not bundled). The CommonJS glue is bundled by Vite;
   its WASM is a hashed same-origin asset passed through `locateFile` (never the glue's own
   `new URL(…, import.meta.url)` default). The glue's Node-only branches reference `fs` and
   `crypto`; Vite externalizes them for the browser build with a warning (they are never
   reached).
2. **Language data:** `@tesseract.js-data/eng` 1.0.0 (MIT package; the data is tessdata_best
   integer, Apache-2.0), file `4.0.0_best_int/eng.traineddata.gz` (2.95 MB on the wire, 5.2 MB
   inflated) self-hosted at `/ocr/eng.traineddata.gz`, inflated in the worker with
   `DecompressionStream` into the module's in-memory FS. **Background precache** (§9). English
   only in Rev 1; more languages are more packages through the same mechanism, with a language
   choice in the dialog then.
3. **Pipeline:** Work worker renders each selected page without a text layer as displayed
   (`/Rotate` applied; PDFium #2, 8-bit gray, 300 dpi, live document) → raster transferred to
   the OCR worker → words with boxes, lines with baselines → Work worker builds the text-layer
   objects (option 3B, `src/workers/work/ocrLayer.ts`, pure and unit-tested) → Render worker
   applies them through `pagesApply` (reopen with objects, ADR-018/M4-20 route) as **one undo
   step**; Ctrl+S is the usual narrow verified tail; the Work copy, caches and the text index
   follow as after any page change (ADR-016 cache map).
4. **The text layer** (ISO 32000-1 9.3.6 render mode 3): per word one `Tm … Tj` whose matrix
   puts the glyphs on Tesseract's baseline (any direction: a sideways scan has vertical
   baselines), font size = the line's ascent above the baseline / 0.905 (Helvetica's AFM
   ascender), the word stretched to its box width from Helvetica's AFM advance widths (a table
   generated from PDFium, unit-tested against it). Non-embedded standard **Helvetica with
   WinAnsiEncoding**: characters outside WinAnsi are dropped (Latin scripts only in Rev 1).
   The original content streams are never touched: `q` before them, `Q` and the text after.
5. **Scope and skipping:** the dialog's page scope (all / current / custom / thumbnail
   selection); pages that already have a text layer (PDFium counts characters) are skipped and
   counted; pages without text and without images are recognized anyway (vector-only scans
   exist). Fixed 300 dpi (200 dpi was as accurate on the fixture and 25 % faster; small print
   decides for 300).
6. **Cancel, progress, memory:** progress per page plus Tesseract's percent within a page; cancel
   between pages through the job's signal, mid-page by terminating the OCR worker (0 ms, a
   fresh one initializes in about 0.3 s). The OCR worker is started on first use and terminated
   when the job ends, so its memory is held only while recognizing (ADR-004 policy for a worker
   whose heap only grows).
7. **Permissions (rule 9):** OCR adds page content, so it needs **modify**; the Render worker's
   `applyObjects` takes the capability it checks (annotate for comments, modify for OCR).
8. **Search in scans, scanned tables** follow without new code: the text layer is real page
   text for PDFium, so Quick Find, Advanced Search, selection, copy, exports and the table
   detectors see it after the usual page-change invalidation.
9. **ARCHITECTURE.md amendments** (applied once this ADR is accepted): §1.5 drop "OCR" and
   "scanned-table extraction" from the non-goals; §3.1 add the OCR worker (tesseract.js-core,
   lazy, terminated after the job) and the OCR flow; §3.2 add tesseract.js-core (Apache-2.0)
   and `@tesseract.js-data/eng` (MIT; data Apache-2.0); new §7.14 "OCR (D-34)" with decisions
   3–8; §9 background precache gains the OCR worker, its WASM and `eng.traineddata.gz`
   (install budget +6.1 MB raw; 7.38 → ~13.6 MB core-equivalent stays within 60 MB); §13 add
   "M5 — OCR"; §14 Rev 1 item 1 marked in progress.

## Consequences

- Scanned documents become searchable, selectable and extractable offline; the output stays a
  standard PDF (a verification item for the owner's Acrobat Reader / PDF-XChange round-trip).
- New runtime dependencies: `tesseract.js-core` (Apache-2.0), `@tesseract.js-data/eng` (MIT).
  Install size +6.1 MB (WASM 2.9 MB, glue 0.1 MB, data 2.95 MB gz; +5.2 MB when inflated at run
  time, in worker memory only).
- A new worker type with its own client and lifecycle; the Work worker gains a raster job and the
  layer builder; `pagesApply` becomes capability-aware.
- Limits accepted for Rev 1: English, Latin characters only in the layer (others dropped);
  no orientation detection (Tesseract's layout analysis handled a 90° sideways page in the
  spike; an upside-down page may not be recognized); no deskew; no "re-OCR a page that has
  text"; no image preprocessing.
- Risks: a page whose original content leaves the graphics state unbalanced can shift the text
  layer (the `q`/`Q` wrap covers the common missing-`Q` case); pages with inherited or shared
  `/Resources` get their own copy with the font added (shared dictionaries are not modified).

## Evidence

Spike code: `spikes/s17-ocr/` (Node: `run-node.ts`, `fixtures.ts`, `layer.ts`, `winAnsi.ts`;
browser: `ocr.worker.ts`, `main.ts`, `s17.spec.ts`, `vite.config.ts`). Results:
`spikes/s17-ocr/out/s17-node.json`, `out/s17-node-200dpi.json`, `test-results/s17-results.json`.
Environment: Node 22.22, headless Chromium (Playwright 1.62) on a 4-core cloud container;
numbers are informative. Fixture: a self-made, fictional pump datasheet (89 words: title at
20 pt, eight 11 pt lines with °, ±, punctuation and numbers; a second copy at 8 pt), rendered
with PDFium and wrapped as image-only pages: page 1 image only, page 2 image plus a separate
vector content stream, page 3 the 8 pt page on a `/Rotate 90` page (a sideways scan), page 4 a
real text page.

Commands:

```sh
node --import ./spikes/shared/ts-ext.ts spikes/s17-ocr/run-node.ts        # → out/s17-node.json
S17_DPI=200 node --import ./spikes/shared/ts-ext.ts spikes/s17-ocr/run-node.ts
SPIKE=s17 PW_CHROMIUM_EXECUTABLE=/opt/pw-browsers/chromium npm run spikes -- --project=s17
```

1. **Core and API.** `tesseract-core-simd-lstm.js` + `.wasm` (89 KB + 2.86 MB) loads in Node in
   22 ms and in a module worker under the verbatim CSP in 37 ms (cold). `TessBaseAPI` binds
   `Init`, `SetVariable`, `SetImageFile`, `SetSourceResolution`, `Recognize`, `GetIterator`,
   `GetTSVText`, `MeanTextConf`, `End`; `ResultIterator` binds `Begin`, `Next`,
   `IsAtBeginningOf`, `GetUTF8Text`, `Confidence`, `getBoundingBox`, `getBaseline` (with
   `has_baseline`). The image goes in as a PGM file written to the module FS (no image codec
   needed; the raster is gray already). `Init(null, 'eng', 1)` (LSTM only) takes 35 ms after the
   2.95 MB gzip is inflated (26 ms Node, 90 ms browser). Tesseract 5.1.0.
2. **Accuracy** (300 dpi, PSM 3): page 1 (11 pt) 88/89 words (the one miss: "400 V" read as one
   token), page 3 (8 pt, sideways) 89/89, mean confidence 92–94. At 200 dpi: 89/89 on all
   three pages, confidence 93.
3. **Speed.** Node: render 92–145 ms, `Recognize` 840–990 ms per A4 page at 300 dpi
   (580–760 ms at 200 dpi). Browser worker: 1,007 ms cold, 720 ms warm, 10 progress callbacks
   per page, round trip from the main thread the same, **no main-thread long task**.
4. **Memory.** Node RSS +130 MB for the Tesseract module after three pages (stable over repeats:
   711, 893, 894 ms). Browser `measureUserAgentSpecificMemory` after two pages: 51 MB.
5. **CSP and network.** Zero CSP violations (page probe and the server's report-only
   endpoint), zero third-party requests, the WASM fetched from `/assets/tesseract-core-simd-lstm-*.wasm`
   and the data from `/ocr/eng.traineddata.gz`, both same-origin.
6. **Cancel.** `worker.terminate()` mid-`Recognize`: 0 ms; the pending call never settles (the
   client rejects it as worker-lost in the product); a fresh worker is ready in 313 ms.
7. **Text layer, option A (PDFium `GenerateContent`):** words found by FPDFText on every page,
   pixels identical, qpdf ok — but the page's content streams were regenerated (page 1: new
   stream 105 instead of 4; page 2: streams 6 and 7 replaced by one stream 196), 89 font
   resource names per page, tail 186,953 bytes.
8. **Text layer, option B (our object layer):** after reopening the saved file, FPDFText finds
   98.9 / 98.9 / 100 % of the fixture's words on pages 1–3 (the saved text layer, i.e. what
   search sees), **89/89 words per page with ≥ 50 % box overlap** between the OCR word box and
   the union of the characters' boxes (mean 0.77), text order as read on the sideways page too,
   pixels identical at 100 dpi, original content streams kept byte for byte (1/1, 2/2, 1/1), one
   font per page, qpdf `--check` ok, tail **13,041 bytes** for three pages (10 objects), built in
   6 ms.
9. **Helvetica widths from PDFium** (20 copies minus 10 copies of each glyph, per 1000 em):
   space 278, A 667, a 556, W 944, i 222, ° 400 — the AFM values.
10. **Characters outside WinAnsi:** `FPDFText_SetText` accepts them for a standard font but
    maps them to arbitrary glyph codes; our layer drops them instead (decision 4).
