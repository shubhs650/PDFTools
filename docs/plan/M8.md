## What a JSON round trip loses today (measured on `main`, 25302ec)

Measured with a new e2e harness (`e2e/json-roundtrip.spec.ts`, `e2e/support/annotDiff.ts`):
each of our self-made interop files (M3 types, replies and states, measurements; M6 comments;
M7 default styles, pasted image, sticky-note pop-ups, text colours, text comments) plus a file
of properties set in the app is exported as JSON, imported into the same file with its comments
removed, saved with Ctrl+S, and compared with the original **annotation by annotation, key by
key** (qpdf's view of both files) and **pixel by pixel** (poppler).

**Lost:**

| What                                                       | Today                                                                           |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------- |
| Stamps: standard, dynamic, image, pasted image             | **Skipped** ("a type a JSON export can't bring"): JSON v1 has no picture.       |
| Attach File comments, with their replies and statuses      | **Skipped**: JSON v1 has no file.                                               |
| Sticky-note pop-up window (position, size, open or closed) | **Lost**: the note comes back without its `/Popup`.                             |
| Pen (ink) drawings                                         | The box grows by about 1 pt on every round trip (re-computed from the strokes). |
| Review-state markers (hidden)                              | Move to the comment's corner; not visible, but not the same.                    |
| Measurement labels                                         | Come back with new ids (a second import is still skipped as a duplicate).       |

**Kept** (no key or pixel difference): geometry, line, border and fill colours, opacity, blend
mode, dashes, cloudy borders and their intensity, line endings, font, bold and italic, size,
alignment, vertical alignment, separate text and border colours (ADR-024), typewriter,
rotation, callouts, measurement dictionaries, replies, review states, author, subject,
creation date, the Locked / Read only / Printable flags, note icons. Text boxes gain a
standard `/DS` key; their look does not change.

## Proposal: JSON version 2 carries the comments' own PDF objects

JSON v1 rebuilds each comment from EmbedPDF's model, so anything the model doesn't hold is lost,
and every new property is one more thing to carry by hand. The app already has a **lossless**
way to move comments: Copy/Paste and Import from a PDF copy the annotation objects as they are
(ADR-018 option 1). Copy builds a small PDF of the copied comments (`copyComments` in the Work
worker: empty pages of the same size, the comments with their appearances, pop-ups, replies,
review states, pictures and attached files).

**JSON v2** = the v1 records as they are (readable by scripts and spreadsheets) **plus that small
PDF**, base64, in one new field. Import:

- a v2 file with the PDF: the chosen comments come in through the **object-copy route** (as
  Paste and Import from a PDF do): every key, every appearance, stamps, attached files,
  pop-ups; one undo step, a narrow verified Ctrl+S.
- a v1 file (or a v2 file whose PDF field was removed): re-created from the records, as today.

The dialog's options (page range, authors, types, statuses, replies, page offset, duplicates by
`/NM`) work the same for both. Future comment properties are kept without any JSON change.

## Task M8-01 — JSON v2 (this thread)

1. **Format.** `docs/formats/pdftools-annotations-v2.md`: v1's fields plus `pdf` (the comments
   PDF, base64) and `pdfPages` (its page i → the document's page). The `annotation` model stays
   for readers. v1 stays frozen and keeps importing.
2. **Export** (the Work worker builds the PDF with `copyComments` and its base64, rule 1;
   cancellable): all comments or the Comments pane's filtered ones, as today. Export Comments
   already needs the **copy** permission (M4-08, rule 9), so the PDF can always be built.
3. **Import**: `parseAnnotationJson` accepts v1 and v2; with a PDF, `importComments` reads it as
   the source (only the planned comments, by `/NM`; page = `pdfPages` + offset; no placement
   transform since the pages are the same size); otherwise re-creation. A damaged PDF field
   refuses the whole file, as a bad record does today.
4. **v1 files** keep importing by re-creation, with today's small differences: a v1 file does
   not carry what would fix them (the state markers' and labels' own rects and ids, the ink's
   saved rect), so they are left as they are; a v2 export has none of them.
5. **Tests.** Unit: v2 parse and validation, v1 still accepted, damaged PDF field refused, the
   plan with filters. e2e: the round-trip harness becomes a permanent spec: **every interop file
   and the in-app properties file round-trip with no key difference** (except `/M`, `/P` and
   object numbers) **and identical pixels**, stamps, attached files and pop-ups included; a v1
   file still imports; Rev A → Rev B with a page offset; the permission case. Perf: 1,000
   comments export and import with no main-thread task > 100 ms.
6. **Docs.** Help (Comment transfer), PROGRESS, ADR-025, ARCHITECTURE.md wording on acceptance.

## Deferred: XFDF and FDF

PDF-XChange- and other-viewer-made comments). The M8-01 harness (key-by-key and pixel compare)
is the base for that work. ADR-018's "XFDF/FDF stay out of Rev 0" stands until then.
