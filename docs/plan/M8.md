# M8 — Lossless comment export and import (XFDF and FDF)

> **Status (2026-11-05):** **proposed**, waiting for the owner's review. No code until the
> plan and [ADR-025](../adr/025-m8-comment-interchange-xfdf-fdf.md) are accepted.

Source: the owner's ask (2026-11-05): "ensure our comments export, import feature works as good
as PDF XFDF, because now we are able to change so many comment properties and sub-properties."
Queued behind the M7 comment tasks, which are done (PRs #81 … #93).

## What we have today (checked on `main`, 25302ec)

There are three ways comments leave or enter a document. Only one of them is lossless.

| Route                                                 | Fidelity                                                                                                                                                                      |
| ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Import Comments from a PDF**, **Copy/Paste**        | **Lossless.** Object copy (ADR-018 option 1): every key and every appearance is copied; spike M4-19 had 33 of 33 pixel-identical. Only `/OC` and `/StructParent` are dropped. |
| **Export Annotations → JSON v1**, then **Import**     | **Lossy.** Re-created through EmbedPDF from its model (ADR-018 option 2). See the list below.                                                                                 |
| **Export Annotations → CSV / XLSX**                   | A report, not an import format. Unchanged by M8.                                                                                                                              |
| **XFDF / FDF**, the files Acrobat and PDF-XChange use | **Not supported.** ADR-018 left them for Rev 1.                                                                                                                               |

What a JSON v1 round trip loses today (from the code and ADR-018 finding 8; M8-01 measures it):

- **Skipped entirely:** stamps (standard, image and pasted, M7-08: v1 has no picture) and
  Attach File comments (no file in v1).
- **Lost keys:** sticky-note pop-up windows (`/Popup` rect and `/Open`, M7-06); measurements
  (`/Measure`, `/IT`, `/LL`, `/LLE`, `/Cap`: a dimension comes back as a plain line); grouped
  labels (`/RT /Group`); rich text `/RC`; other viewers' private keys.
- **Changed look:** appearances are regenerated, so comments made in other viewers (custom
  fonts, callouts, measurement labels, cloudy shapes) can look different.
- **To verify in M8-01:** text colour separate from border colour (ADR-024, `/DS`), blend mode,
  the Locked / Read only / Printable flags, line style and dash pattern, cloud intensity, the
  typewriter's Courier, the B15 grown rect, review states with their authors and dates.

So "as good as XFDF" is not true today for files: a user who exports comments and imports them
into the next revision gets a weaker copy than the one copy/paste or PDF import gives.

## Proposal in one paragraph

Add **XFDF** (ISO 19444-1, Acrobat's and PDF-XChange's XML comment file) and **FDF** (PDF
32000-1 §12.7.8, the binary one) to Export Annotations and Import Comments. Both are built on the
lossless object-copy route we already have: export reads each comment's PDF objects (dictionary,
pop-up, replies, review states, appearance streams, image and attached file) and writes them out;
import turns the file back into PDF objects and applies them exactly like an import from a PDF
(one undo step, narrow Ctrl+S, ADR-005 verification). Our own files round-trip exactly, files
from Acrobat and PDF-XChange import with everything those viewers put in them, and our files
open in those viewers. JSON v1 stays as it is, a data export (Q2).

## Tasks

### M8-01 — Spike S26: the property matrix, and XFDF/FDF as the other viewers write them

- **Matrix harness** (Node, real PDFium, like S16): a self-made fixture with one comment per
  type × every property the app can set today (the Properties pane's list in
  `properties/model.ts`, the flags, the note icon, pop-up rect and open state, replies and
  nested replies, review states and Marked, grouped labels, measurements, standard / image /
  pasted stamps, Attach File, text box / typewriter / callout with ADR-024 colours, rotation,
  B15-grown rects), plus a page of hand-written "other viewer" comments (`/RC`, `/DS`, custom
  appearances, private keys). The harness compares each comment before and after a round trip
  **key by key** and **pixel by pixel**. First run: JSON v1, to record today's loss as the
  baseline.
- **Mapping table** for every key we meet: PDF key ↔ XFDF attribute or element (`<contents>`,
  `<contents-richtext>`, `<defaultappearance>`, `<defaultstyle>`, `<popup>`, `<appearance>`,
  `<imagedata>`, `<data>`, `<measure>`, `vertices`, `inklist`, `coords`, …) ↔ FDF (objects as
  they are). What XFDF cannot carry (other viewers' private keys) is written down; FDF carries it.
- **Real files from the other viewers** (Q3): the owner's PDF-XChange (and, if possible,
  Acrobat) XFDF and FDF exports of our self-made interop PDFs. The spike checks which elements
  they write, how they encode appearances, stamps and attachments, and whether they read our
  appearances back.
- **XML parsing in a worker** (no `DOMParser` there): our own small reader for the XFDF subset
  (elements, attributes, text, CDATA, the five entities and character references), which
  **refuses any DOCTYPE** (no entity expansion), with size limits. No new dependency. Writer the
  same.
- Outcome and numbers go into ADR-025's Evidence. If something the plan assumes is impossible,
  the thread stops and reports options (CLAUDE.md).

### M8-02 — Export to XFDF and FDF

- Comment → **Export Annotations** gains **XFDF** (first, the default) and **FDF** beside CSV,
  XLSX and JSON; "All comments" or "Comments shown in the Comments pane" as today.
- Built in the **Work worker** from the document's current state (its read-only copy plus the
  live section): every comment with its pop-up, replies, review states, appearance streams,
  stamp images and attached files. XFDF: `<f href>` is the document's name and `<ids>` its `/ID`;
  appearances in `<appearance>` (Q4). FDF: `%FDF-1.2`, `/FDF << /F … /ID … /Annots [ … ] >>`,
  each annotation with `/Page`.
- Needs the **copy** permission, as the JSON export does (comment text is content, rule 9). An
  encrypted document is written out decrypted (the file is the user's own export, as JSON is).
- Cancel and progress; 1,000 comments with no main-thread task > 100 ms (perf test).

### M8-03 — Import from XFDF and FDF

- Comment → **Import Comments** accepts `.xfdf` and `.fdf` beside `.pdf` and `.json`, with the
  same options: page range, author / type / status filters, with or without replies, page offset;
  duplicates skipped by `/NM`.
- Strict validation (format, version, sizes; one bad annotation refuses the file, as JSON does);
  the file is turned into annotation objects in the Work worker and applied through
  `SaveTracker.applyObjects`, the route PDF import uses: one undo step, the next Ctrl+S writes
  one narrow, verified revision, recovery covers it.
- Placement: same page coordinates (XFDF and FDF carry no page boxes; this is what Acrobat and
  PDF-XChange do). Comments outside the page's crop box are counted in the report.
- Annotations without an appearance (XFDF files written without `<appearance>`) get PDFium's
  generated appearance, as today; stamps without a picture are listed and skipped.
- The target needs **annotate**; an encrypted target gets the objects encrypted with its key
  (the M4-20 route). When the file was made for another document (`<f href>` / `/F`, `/ID`), the
  dialog says so, but the import is allowed (that is the Rev A → Rev B case).

### M8-04 — Round-trip every property, and fix what is lost

- The M8-01 matrix runs in the unit suite for **Triya → XFDF → Triya** and **Triya → FDF →
  Triya**: every comment equal key by key (except `/P`, object numbers and remapped references)
  and pixel-identical. Anything lost is fixed in this task.
- The owner's PDF-XChange / Acrobat files (or, without them, hand-written ones per the spec, rule 13) import with every element they carry.
- e2e: make one of every comment in the app, edit their properties, export XFDF and FDF, import
  into a clean copy of the file, compare the Comments pane and the Properties pane value by
  value, save, reopen, compare again. Same for a Rev A → Rev B transfer with a page offset.
- Perf: 1,000 comments export and import into the 2,000-page stand-in, 0 main-thread long tasks.

## Explicitly not in M8

- Opening an `.xfdf` / `.fdf` from File → Open (Acrobat then opens the linked PDF and imports):
  import goes through Import Comments only (Q5).
- Form-field data in FDF/XFDF (`<fields>`): comments only. Form data import/export is its own
  feature.
- Other XFDF dialects (Bluebeam, PDFTron/Apryse "command" XFDF): imported only as far as they
  follow the standard; no special cases.
- Changing JSON v1 (frozen) unless the owner picks Q2 b.
- Revision compare (parked, rule 14).
