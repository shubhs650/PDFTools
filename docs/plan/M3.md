## M3-03 — PDF object layer in the workers + single-revision merge

> **Status (2026-09-27):** done. `src/model/pdf/{objects,reader,wire}.ts` (values, parser,
> serializer, async reader with `DecompressionStream`, RPC wire form); staged patches in
> `src/workers/render/objects/patches.ts`, applied by the tracker to PDFium's own serialization
> of the target object inside the **single** narrow tail (new `patches` option of `narrowTail`).
> **Design detail:** PDFium's in-memory objects never hold our keys, so a patch is _sticky_: it
> is re-applied whenever a later save rewrites the object, and Save Optimized appends the patched
> objects as one small section after the rewrite (otherwise it would drop them). Only measurement
> keys (`/Measure`, `/IT`, `/Cap`, `/CP`, `/LL`, `/LLE`, `/LLO`, `/CO`) on annotations and `/VP`
> on pages can be staged; `/Contents` goes through EmbedPDF. Strings in encrypted files are
> refused (`patch-encrypted`) until M3-04. New Render RPC `stageObjects`; `saveState.staged`;
> digest `objects` checked by the Work worker with our reader (`verifyObjects.ts`, new mismatch
> reason `objects`). `revision.ts` was not ported: the merge replaces it. `scale-math.ts` and
> `read-measure.ts` move with M3-15/M3-16. The Layers pane reads through the shared reader, with
> the old scanner as a fallback for damaged files.

**Goal.** Port the S2 object layer so the Render and Work workers can read and write the
structures EmbedPDF/PDFium can't (`/Measure`, `/IT`, `/Cap`, page `/VP`), and merge our objects
into the **single** Ctrl+S revision (ADR-007 decision 5).

**Refs.** D-14, §7.4, ADR-007 decisions 1 and 5, ADR-005, M1-20 (`extra` hook in `narrowTail.ts`),
rule 7.

**Depends on.** —

**Files likely touched.** `src/workers/render/objects/{pdfObject.ts,serialize.ts,revision.ts}`
(or `src/model/pdf/` if the Work worker shares them), `src/model/ocg.ts` (switch to the shared
reader), `src/workers/render/save/{narrowTail.ts,tracker.ts,digest.ts}`,
`src/workers/work/verifySave.ts`, `tests/objects/*`, `tests/save/*`.

**Acceptance criteria.**

- Reader handles xref tables and streams, predictors, `/Prev` chains, hybrid `/XRefStm`, object
  streams and PDFDocEncoding/UTF-16BE strings; inflate via `DecompressionStream` (no Node zlib,
  no new dependency). Reals serialized with 10 significant digits, never exponent form.
- Fails loudly on anything it can't read (encrypted strings until M3-04) — never misreads.
- Render-worker API to stage "extra" objects/keys for a document (e.g. add `/Measure` to annotation
  N, set page `/VP`); the next Ctrl+S emits **one** revision containing PDFium's changed objects and
  ours, qpdf-clean; M1-21 verification covers the staged keys (digest extended).
- Staged edits are undoable (they are cleared/rewritten with the owning annotation) and survive
  recovery (they are in the recovery tail).
- The Layers pane's reader (`ocg.ts`) uses the shared reader with no behavior change.

**Tests.** Ported S2 unit tests (19); reader vs qpdf page/object counts on every unencrypted
fixture; save matrix: 8 S1 originals × (annotation + staged `/Measure` + `/VP`) → one revision,
qpdf-clean, values read back exactly, second Ctrl+S appends only new changes; verification catches
a deliberately dropped staged object (keep-all fallback).

## M3-04 — Standard security handler (encrypted files)

> **Status (2026-09-27):** done. `src/model/pdf/security/` — own MD5, RC4 and AES-CBC (sync, as
> the save path needs; unpadded CBC for R6), SHA-2 from WebCrypto for R5/R6 key derivation;
> Algorithms 2, 6, 7, 2.A and 2.B; RC4, AESV2, AESV3 and Identity crypt filters. The reader
> decrypts strings per object and streams in `decode`; the Render worker derives the file key
> from the open password (memory only) and encrypts only our values; the Work worker's check
> decrypts with the same password. Public-key handlers still refuse strings (`patch-encrypted`).
> The interim "can't be saved" message belongs to the measurement UI (M3-15/16), which now only
> needs it for unsupported handlers.

**Goal.** Read and write strings and streams in encrypted files for our object layer, so
measurement and viewport data can be saved in encrypted PDFs (ADR-007 decision 4, option 1).
Until this lands, measurements in encrypted files are shown but not saved, with a message.

**Refs.** D-14, D-19, §7.4, ADR-007 d4, ADR-013 (permission map), M2-Q7 (passwords in worker
memory only), M3-Q8, rule 9.

**Depends on.** M3-03, M3-Q8.

**Files likely touched.** `src/workers/render/objects/security/{standard.ts,rc4.ts,md5.ts,aes.ts}`,
`src/workers/render/objects/pdfObject.ts`, `src/workers/render/save/tracker.ts`,
`tests/objects/security/*`, `e2e/fixtures/encrypted.ts`.

**Acceptance criteria.**

- File-key derivation for R2–R4 (MD5/RC4, 40–128-bit, `/EncryptMetadata`) and R5/R6
  (SHA-256/384/512, AES-256); per-object keys for RC4 and AESV2; AESV3; crypt filters
  (`/StmF`, `/StrF`, `/Identity`).
- The key comes from the password the user already typed (held in worker memory only, M2-Q7) or
  the empty user password; never stored, logged or reported (rule 10).
- Writing respects the permission map: no staged object is written without the annotate
  capability (rule 9). R, P and method unchanged after save (qpdf).
- The interim "can't be saved in encrypted PDFs" message disappears for supported handlers and
  stays for unsupported ones (public-key handlers).

**Tests.** Unit: MD5/RC4 against RFC 1321 / RFC 6229 vectors; decrypt qpdf-encrypted fixtures
R2, R3, R4, R6 (strings, streams, object streams) and compare with qpdf's `--decrypt` output;
round trip: stage `/Measure` + `/VP` on each, save, `qpdf --check`, read back with qpdf decrypted.
E2E: measure in an encrypted file after M3-16 (added there), and a scan proving no password in
IndexedDB/OPFS (extends the M2-03 scan).
