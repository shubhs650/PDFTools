## Explicitly **not** in M1

Search / find bar, thumbnails / bookmarks / attachments panes, text selection and copy, print,
password prompt for protected PDFs, forms, signature pane, error-report endpoint (all M2);
annotations, undo/redo, reviewer profile, measurement, snapping (M3); extraction, page operations,
redaction (M4); revision compare (parked, rule 14). M1 builds the **frames** these plug into
(rail, Properties pane, command table, Work-worker scheduler) but no pane or command content for
them.

Because M1 has no user-facing edit, save and recovery are exercised through a **test-only mutation
hook** (M1-02, M1-20) that exists only in the `e2e` build mode, never in the production build.

## M1-01 — EmbedPDF plugin-layer spike (ADR-011)

> **Status (2026-09-25):** agent part done — _Works with workaround_,
> [ADR-011](../adr/011-m1-embedpdf-plugins.md) (accepted). Consequences are folded into M1-07, M1-13,
> M1-14, M1-16 and M1-17 below.

**Goal.** M0 exercised EmbedPDF's _engine_ only; S3/S5 drove tiles with our own viewport code.
Before building the viewer on `@embedpdf/core` and the headless plugins, confirm (CLAUDE.md
workflow: "spike first") that they meet §5 and ADR-004 on top of the **hosted** engine.

**Refs.** D-09, D-10, §5, ADR-004 decisions 2–3.

**Depends on.** —

**Files likely touched.** `spikes/s9-plugins/*` (throwaway), `docs/adr/011-m1-embedpdf-plugins.md`,
`package.json` (add `@embedpdf/core` and plugins, pin every `@embedpdf/*` to exact `2.15.1`),
`docs/plan/M1.md` (adjust M1-14..17 if needed).

**Questions to answer.**

1. Do `plugin-viewport`, `-scroll`, `-render`, `-tiling`, `-zoom`, `-spread`, `-rotate` (and the
   document manager / loader) run over a `PdfEngine` built on our hosted executor?
2. Multiple open documents: one plugin registry per document, or one registry with a document
   manager? What does each cost in memory and startup?
3. Can we set the tile size to 256 px, and abort **queued** stale tiles on every scroll/zoom change
   (ADR-004 decision 3)? If not, which hook lets our code do it?
4. Zoom range 1 %–6400 %; "scaled preview first, sharp tiles later" behavior.
5. Where a render > 100 ms would be issued (full-page preview at high zoom) and whether we can
   route it to our progressive path.
6. Which plugins pull in network defaults (fonts, WASM) that must be overridden.

**Acceptance criteria.**

- ADR-011 written with outcome Works / Works with workaround / Blocker per question, and the
  plugin list M1 will use.
- If any answer conflicts with ARCHITECTURE.md, the ADR stops and proposes options (CLAUDE.md
  "stop and report"); M1-14+ wait for the owner.
- License gate passes with the added packages; all `@embedpdf/*` pinned exactly.

**Tests.** Spike Playwright page: 2,000-page stand-in scrolled under the §10.1 CSP, recording
long tasks, tile latency and aborted-tile counts (numbers go in the ADR).

> **Status (2026-09-25):** done on branch `m1/02-e2e-harness`. Differences from the sketch below:
> each Playwright worker starts its own `scripts/serve.ts` (so CSP reports never mix between

**Goal.** Every later e2e and perf test runs against the **built** app, served the way Cloudflare
Pages serves it, with the §10.1 CSP enforced and shared probes for long tasks, CSP violations and
outbound requests. This delivers the "CSP" scope item.

**Refs.** D-22, D-27, §10.1, §11, ADR-003 decisions 1–2 and 4, ADR-004 decision 5, rule 4.

**Depends on.** —

**Files likely touched.** `public/_headers` (CSP verbatim + COOP/COEP), `scripts/serve.ts`
(promoted from `spikes/shared/serve.ts` + `headers.ts`), `playwright.config.ts` (webServer =
`vite build --mode e2e` + `scripts/serve.ts`), `e2e/support/probes.ts` (from
`spikes/shared/probe.ts`), `e2e/support/fixtures.ts`, `e2e/fixtures/generate.ts` (self-made PDF

**Tests.** Unit: `_headers` parser/applier (ported from the spike), fixture generators produce

## M1-03 — Typed RPC and job infrastructure

> **Status (2026-09-25):** done on branch `m1/03-rpc`. API specs are declared with `MethodSpec<Args, Result, Progress>`; zero-copy results use `new Transfer(value, list)`; unknown errors cross as their class name and stack frames only (rule 10).

**Goal.** One typed, cancellable, progress-reporting RPC used by every worker (rule 2).

**Refs.** D-10, §3.1, ADR-004, rules 1–2, rule 10.

**Depends on.** —

**Files likely touched.** `src/engine/rpc.ts`, `src/engine/jobs.ts` (job handle: `promise`,
`cancel()`, `onProgress`), `src/engine/errors.ts`, `src/workers/rpc-host.ts`, `tests/engine/*`.
Ported from `spikes/s3-two-engines/rpc.ts`.

**Acceptance criteria.**

- Request/response typed end to end from one method map per worker (compile error on a wrong
  argument or result type).
- `AbortSignal` → cancel message; the worker sees an aborted signal; the caller's promise rejects
  with `AbortError` exactly once, even if a late result arrives.
- Progress events throttled to ≤ 1 per 100 ms; jobs > 300 ms must declare progress (dev assert).
- Transferables passed without copying; errors cross the boundary as `{code, message, stack}` with
  no document content (rule 10).
- Worker crash rejects all pending calls with a typed `WorkerLost` error and allows respawn.

**Tests.** Unit (Vitest, in-memory `MessageChannel`): happy path, cancel before/while running,
late result after cancel, progress throttling, transfer, error serialization, worker loss.

## M1-08 — Work worker (M1 scope) and memory policy

> **Status (2026-09-25):** done on branch `m1/08-work-worker`. Jobs go through `WorkClient.run(method, args)`; documents open with a `reload()` source so a respawn can re-derive the original; `refresh(docId, tail)` is the hook M1-21 uses after each save.

**Goal.** PDFium #2 in the Work worker with a read-only copy of each document, lazy refresh
(original + tail), a priority job scheduler, and the respawn memory policy. M1 uses it for save
verification; M2 adds search.

**Refs.** D-10, §3.1, ADR-001 B11, ADR-004 decisions 1 and 4, ADR-006 decision 3 (scheduler
shape only).

**Depends on.** M1-03, M1-07.

**Files likely touched.** `src/workers/work.worker.ts`, `src/engine/workClient.ts`,
`src/workers/work/scheduler.ts` (priorities: interactive > save-verify > background; pause/resume
background; cancel), `src/workers/work/docs.ts` (open, refresh with tail, evict),
`src/engine/workerLifecycle.ts` (respawn: idle after a job whose WASM peak > 256 MB; on eviction;
reload remaining docs as original + tail), `tests/work/*`.

**Acceptance criteria.**

- Receives the original bytes by transfer; Render worker gets its own copy (§3.1).
- `refresh(docId, tail)` is lazy: applied on the next Work job, never a full re-serialization.
- Scheduler: a higher-priority job preempts background work at the next page boundary; background
  jobs pause while a save runs.
- Respawn policy implemented and observable (`memory()` probe reports WASM `byteLength`); after
  respawn, open documents are usable again without user action.
- The Render worker is respawned only when no document is open.

**Tests.** Unit: scheduler ordering/preemption/cancel, respawn decision function (thresholds,
idle, eviction), refresh bookkeeping. E2E: open a doc in both workers, force a large job, verify
respawn returns memory to baseline and the doc still works.

## M1-12 — Storage layer (IndexedDB, OPFS, file access, fingerprint)

> **Status (2026-09-25):** done on branch `m1/12-storage`. Pure state machine `saveMachine.ts` (idle → saving → verifying → writing → done / error / cancelled; cancel until the write commits). Errors are localized with a Save As offer where it helps (`SaveStatus.tsx`: status-bar phase + Cancel, error dialog). The tab's dirty mark now comes from the engine proxy (`onMutation` for every successful mutating call, method list shared in `src/engine/mutations.ts`); an edit made during a save keeps the tab dirty (edit counter). After the app writes to a handle, the pre-save `File` snapshot is unreadable, so the original bytes are read back as the file's prefix (`originalBlob`, also used by the Work worker's reload). Measured: Ctrl+S with 100 markups on a 3-page file 134 ms, no long tasks.

**Goal.** Incremental save to the original handle and Save As to a new location, with dirty state
and fallbacks.

**Refs.** D-04, D-06, §4.2, ADR-001 B12, ADR-005, rules 2, 7.

**Depends on.** M1-10, M1-11, M1-12, M1-13, M1-21.

**Files likely touched.** `src/features/save/save.ts`, `saveAs.ts`, `src/features/save/
SaveStatus.tsx`, ribbon/backstage/keymap wiring, `tests/save/commands.test.ts`,
`e2e/save.spec.ts`, `e2e/perf/save.perf.ts`.

**Acceptance criteria.**

- Ctrl+S appends the verified tail to the original handle (`keepExistingData`); the tab's dirty
  mark clears; appended bytes are tracked per document (for M1-23).
- No handle (dropped file, Firefox) → Ctrl+S acts as Save As; Firefox Save As = download.
- Save As writes original + tail (incremental copy) to a new handle, which becomes the document's
  handle; "optimized" choice routes to M1-23.
- Write permission denied or handle gone → localized error, offer Save As; the original file is
  never partially written (abort before commit).
- Save is cancellable before commit; 100 test-hook markups on a small file save in < 1 s with no
  long tasks.

**Tests.** Unit: save state machine (idle → saving → verifying → writing → done / error /
cancelled). E2E: Ctrl+S twice (second no-op), Save As, reopen saved file and count annotations,
permission-denied path; perf: 100 markups < 1 s.
