## The feature in one page

Engineers get two kinds of revised PDFs:

- **Drawings** (CAD exports, scans of drawings): the question is "what moved, what was added,
  what was removed". The tool is the **PDF overlay**: the old revision in one colour, the new
  one in another, laid on top of each other, with everything that is the same shown **black**.
- **Text documents** (tenders, specifications, purchase orders, invoices, calculation reports,
  inspection reports): the question is "which words, numbers, clauses and table rows changed".
  The tool is the **text comparison**: old and new side by side with every change marked.

Both ship together in one release (Q2). Both follow the same shape:

1. **A comparison is its own tab** (Q13). It opens on an input window: Document A (old) on the
   left, Document B (new) on the right, a Compare button. Good defaults mean two files and one
   click are enough (Q35).
2. **The result appears in the same tab**, first sheet first, the rest filling in behind it
   (Q40). A list of differences sits in the right pane; each entry can be ticked as checked.
3. **The reviewer works in the result.** The overlay is a reference picture; the real work is
   closing out the old revision's comments against the new revision, and writing new comments
   (Q15). Every comment tool and right-click menu works in every window of the comparison.
4. **Two ways to save** (Q20). **Save review** (Ctrl+S) writes the reviewer's new comments into
   Document A and Document B, as ordinary comments. **Save comparison…** writes one
   **comparison file**: a standard PDF that any reader can open, and that reopens in Triya PDF
   as the live comparison (Q19, Q33).
5. **A change register** (Excel or CSV) lists every difference for the record (Q34).

Nothing leaves the device, nothing needs a network, and no AI is involved (Q39).

### 2. What is missing

- **The view shows one document at a time.** One host, one active document. A comparison needs
  two or three documents on screen together, each with working comment tools, scrolling in step.
  ARCHITECTURE.md §14 reserved "a future two-document synchronized view" as an extension point,
  but nothing is built. This is the largest unknown and gets the first spike (S27).
- **No way to draw two pages on top of each other**, no alignment, no difference detection, no
  text diff. All new.
- **A page can be rendered only in its own position.** The overlay needs the old revision drawn
  shifted, scaled and rotated into the new revision's position. PDFium can render a page through
  any matrix; EmbedPDF's engine does not expose it, so it is a direct PDFium call (allowed by
  D-09).

### 3. Limits set by the browser

- **A web app cannot find a file again by its path.** A saved comparison cannot point at
  `C:\…\RevA.pdf`. So the comparison file has to carry the two documents inside it (Q19).
- **Saving back into a file needs the file's handle** (File System Access API, D-04). A file
  that was dropped or picked keeps a handle in Chrome and Edge; elsewhere Save review falls back
  to a download, as Ctrl+S already does.
- **Memory.** A comparison holds two documents open (three with the overlay document). §12's
  budget of 2 GB for five heavy tabs stays the reference; S27 and S29 measure it.

### 4. Thin CAD lines

The owner's concern (Q4): drawings exported with zero-thickness lines almost vanish in a
pixel-based comparison. Two facts shape the design:

- A zero-width line is drawn **one device pixel wide at every zoom** by every PDF engine, vector
  or not. It never gets thicker by zooming in. What makes it vanish in other tools is comparing
  one fixed-resolution picture and then zooming that picture.
- So the on-screen overlay **re-renders both revisions at the current zoom** (the same tiles the
  normal view uses) and only then combines them. Lines stay as sharp as in the normal view at
  any zoom up to 6400 %. A **Thicken thin lines** switch makes hairlines 3 pixels wide for
  readability (Q18). The true **vector overlay** is built as well (below).

### 5. The corpus

`Synthetic PDF Corpus/` (4.9 MB, on `main` since #144) covers the logic cases well: shift and
scale, skew and page rotation, an inserted sheet, scans at different resolutions, colour to
mono, hairlines and micro-text, page boxes, layers, encrypted files, large sheets; numeric
tables, images, formulas, two columns, clause renumbering, formatting noise, a long table, a
scanned appendix, reordered sections, a long tender, four scripts and OCR artifacts.

What it does not test: every file is generated by one tool, is sparse (5 to 10 KB a page) and
uses one standard font. No file has the weight of a real CAD export (tens of thousands of
lines, zero-width lines, hatching, text drawn as curves), and none exercises the review flow
(old comments to close out). The owner agreed to add pairs (Q37, task M12-01).

Housekeeping found on the way: `.gitignore` blocks `*.pdf` outside `e2e/fixtures/self-made/`
(the corpus was added by upload), and the folder name has spaces. The folder stays where it is
(Q37); M12-01 adds the ignore exception and one loader that every test uses.

## Design

Terms used below: **Document A** is the old revision, **Document B** the new one. In an overlay
comparison each can be a set of files (Q38). A **sheet** is one pair of pages, one from A and
one from B (or a page that exists on one side only).

### Starting a comparison (D-58)

- **Compare** is a new ribbon tab, between Convert and Protect. Commands: **PDF Overlay**,
  **Text Comparison**, and, inside a result, the commands of that result (below). The document
  tab menu gains **Compare with…** (Q43).
- A comparison is **a tab in the document tab strip** (Q13), with its own icon and a name such
  as "RevA ↔ RevB". Several can be open. The tab first shows the **input window**:
  - Two sides, **Document A (old)** and **Document B (new)**. Each takes a dropped file, a
    picked file, or a document that is already open in a tab. A **swap** button exchanges them.
  - Each side shows its document as thumbnails with a **page range** (Q35).
  - **PDF Overlay** only: each side accepts **several files as one set** (Q38), and a **pairing
    table** shows which page is compared with which (below). No folder picker.
  - A collapsed **Options** section, and a **preset** list (Q35). A preset holds colours, ignore
    zones, sensitivity and header handling; it is saved from a result and stored on this device.
  - **Compare** runs with the defaults. The inputs can be revisited from the result.
- A document that is open in its own tab and in a comparison is **one document**: one set of
  comments, one undo history, one unsaved mark (Q43).
- A result has a button to **run the other comparison type on the same files** (Q43).
- **Protected files** (Q25): each action follows each file's own flags. Looking at a comparison
  is viewing and is always allowed. Commenting needs the commenting permission of that file.
  Copying text from the list, exporting the overlay, the change register and saving a
  comparison file need the content-copying permission of both files. The permissions password
  unlocks. A blocked action says which file blocks it and why. Nothing is bypassed (rule 9).

### Pairing pages (D-60)

- Pages are paired **automatically by similarity** (Q9): each page gets a small signature (a
  coarse picture of its ink and a fingerprint of its text). Matching keeps page order where it
  can and still finds **inserted, removed and reordered sheets**. With several files per side,
  file names help the match. No title-block reading.
- The pairing table is **editable**: change a partner, mark a page as added or removed, exclude
  a sheet. It shows file names when a side has several files.

### Alignment (D-60)

- **Check first, align only when needed** (Q5). Each sheet is first compared as it is and
  scored. Only a sheet that matches poorly is aligned automatically. Each sheet shows its
  status: **as is**, **auto-aligned** (with the shift, scale and rotation found), or **low
  confidence, needs points**.
- The transform is **shift, one scale for both directions, and rotation**, nothing else. The
  drawing is never stretched unevenly. The old revision is drawn in the new revision's position.
  Page rotation (`/Rotate`) and page boxes (CropBox against MediaBox) are part of the transform,
  so corpus pairs 04 and 09 align without special cases.
- **How** (Q6) is decided by spike S28 between two routes, on accuracy, time and install size:
  1. **Our own geometry aligner** for vector pages: feature points from the line geometry the
     snap index already extracts (line ends, corners, crossings), matched with RANSAC to a
     similarity transform and refined by least squares; for scans, an image method (phase
     correlation for the shift, its log-polar form for rotation and scale, coarse to fine).
  2. **OpenCV** (Apache-2.0) feature matching (ORB). It is used **only if scans need it**, and
     then loaded on demand like an OCR language, never in the core.
- **Manual alignment on any sheet** (Q7, Q8): pick **1 to 3 point pairs** (1 = shift; 2 = shift,
  scale and rotation; a 3rd gives a best fit and shows the error). Picking **snaps to the
  drawing** with a magnifier. **Numeric fine-tune**: X and Y offset, scale %, rotation °, arrow
  keys nudge. **Apply to**: this sheet, all sheets, or all low-confidence sheets.

### The overlay on screen (D-59)

- **Colours** (Q12): old = red, new = green, the same = black. Presets red/blue and
  magenta/green (safe for colour-blind users). Custom colours through the standard swatch
  picker, with a warning when the two chosen colours would not give a dark overlap.
- **How it is drawn** (Q4): each revision is rendered at the current zoom **without its
  comments**, turned to grey, tinted with its colour, and the two are combined with **Multiply**.
  Red ink over green ink multiplies to black; ink over white paper keeps its colour. Only
  Multiply is offered, no list of blend modes. Whether the combining happens in the browser's
  compositor or in a worker is settled by spike S29; either way the main thread does no pixel
  work (rule 1).
- **Comments stay themselves** (Q10): comments of A and B are not part of the comparison. They
  are drawn on top in their real colours, with a switch per document. Markups that were
  flattened into the page are content and are compared.
- **Hide check highlights** (Q11): one switch hides the reviewer's "this part is checked" marks:
  every Highlight comment and anything more see-through than 70 %.
- **Layers** (Q24): each file is compared with its own default layer visibility. Layer switches
  per document update the overlay and the differences. A notice appears when a layer's default
  differs between the two files.
- **A floating bar** over the overlay (Q18): show or hide old, show or hide new, a **balance**
  slider (old only ↔ both ↔ new only), **Fade unchanged** (dims the black so the colours stand
  out), **Thicken thin lines**, and **Blink** (hold a key to flip between old and new). No
  curtain or wipe slider.

### The vector overlay (D-59, beta)

- A **true vector overlay PDF** is built by one builder and used twice (Q4): as the visible
  pages of the saved comparison file and for **Export Overlay…**, and as a **beta display mode**
  in the result ("Vector overlay (beta)"), which gives the look of a single PDF at any zoom.
- Route, decided by spike S29, in order of preference:
  1. **Wrap and tint.** Each source page becomes a reusable form inside the new PDF, untouched.
     It is painted as a solid tint through a mask made from the page itself, and the second
     revision is laid over the first with the standard Multiply blend mode (PDF 1.4
     transparency). The original drawing instructions are never rewritten, so nothing can be
     lost.
  2. **Recolour.** Rewrite the colour instructions of a copy of each page to the tint, then
     Multiply. Smaller files and faster drawing, but images, shadings and nested forms each need
     their own handling.
  3. **Fallback:** a high-resolution image overlay PDF, if neither route displays correctly in
     Acrobat Reader and other viewers.
- The spike checks the result in Acrobat Reader, a second desktop PDF editor, and the built-in
  viewers of Chrome, Edge and Firefox, and measures drawing speed at deep zoom and file size.

### Differences on drawings (D-61)

- The overlay **also finds the differences** (Q3): a list, next and previous, sheets with no
  change flagged as unchanged.
- **Detection** runs on the aligned pair at a fixed analysis resolution, in a worker. A mark of
  one revision counts as unchanged when the other revision has ink within a small tolerance of
  it; this ignores anti-aliasing and sub-pixel shifts. What is left is grouped into regions:
  **added**, **removed** or **changed**.
- **Text-aware** (Q23): the positioned text of both pages is compared as well. An entry reads
  "Ø120 → Ø128" instead of "region 14", and is labelled **text**, **geometry** or **both**.
  Scanned sheets have no text and fall back to regions.
- **Tuning, live** (Q22): sensitivity (low, normal, high) and a minimum change size apply
  without a new run. **Ignore zones** are rectangles (a title block, a revision table) for one
  sheet or all sheets, saved as named sets.
- **The list** (right pane, Q17, Q43): filter by kind and sheet, search, next and previous
  keys, a **checked** tick per entry. The **sheet list** shows done, changed or unchanged and
  the percent changed, and sorts by it. Thin outlines mark the regions on the overlay; they are
  view-only and can be switched off.
- **Make cloud comments** (Q17) turns the selected regions, or all of them, into real cloud
  comments on the new revision, on request. No clouds are made automatically.

### Review across revisions (D-62)

The owner's review flow (Q15): the reviewer goes through the **old revision's comments** and
checks each against the new revision. Addressed: mark the old comment done and highlight where
it was fixed. Not incorporated: copy the comment to the new revision, then mark the old one
done. Changed to something else: mark the right value on the new revision, then mark the old
one done.

- **Layout switch** (Q14): **Overlay only**, or **Review**: the overlay large on the left,
  Document A top right, Document B bottom right, with draggable splitters. A result opens in
  Review. One sheet at a time, no continuous scroll. The windows do not swap places.
- **All three windows are live** (Q15): every comment tool, the Properties pane and every
  right-click menu (copy, paste, delete, status, flatten and the rest) work in each window.
- **The overlay is for reference only** (Q15): anything drawn on the overlay window is a note
  of the comparison. It is stored in the comparison file and is never written into Document A
  or B.
- **Aligned sync** (Q21): the three windows show the same spot of the drawing, through the
  alignment, at matching zoom. The lock is on by default. A **linked pointer** shows a crosshair
  at the same spot in the other two windows.
- **Aligned copy** (Q16): **Copy to new revision** (and the reverse) puts a comment at the
  matching spot on the other revision. Paste between the windows lands at the matching spot too.
- **Close-out tracking** (Q16): a list of every comment of the old revision with its state. One
  click marks a comment **Addressed**, **Carried over** (which also copies it) or **Changed
  differently**, and applies the green check highlight to it (colour adjustable). The states
  use the existing comment status, so they reach the CRS export (see Question 1).

### Text comparison: what is compared (D-63)

- **Kinds of change** (Q26): **inserted**, **deleted**, **replaced**, **moved** (reported once,
  with a link between the two places, and any edit inside the moved text still shown), and
  **changed figure** (pictures compared as pictures, shown before and after). A change of
  formatting alone (font, size, bold) is not reported.
- **Word level, with engineering values kept whole** (Q27): `1,450.00 mm`, `P-101A`,
  `2026-11-22`, `DOC-4410-REV2` are each one unit. A changed number shows its **percent
  change** in the list. Units are not converted.
- **Method** (spike S30 settles the details): text is read in reading order, column by column
  (recursive XY-cut), and normalised (line-end hyphens, ligatures, spacing). Paragraphs are
  matched first (unique paragraphs as anchors, then Myers' difference algorithm), then words
  inside each matched pair. A deleted and an inserted block that are nearly the same become one
  **move**.
- **Headers and footers** (Q28, experimental): text that repeats from page to page and running
  page numbers are found automatically and left out. A header that changed is reported **once**.
  A switch includes them; bands drawn by hand override the detection.
- **Tables** (Q30): where a table is recognised, rows are matched as rows. An inserted or
  deleted row is one change; a changed cell is reported with its row and column; a column header
  repeated on each page is not reported. Anything else falls back to running text.
- **Clause renumbering** (Q31, experimental): when a clause is inserted and the following
  numbers all shift, that is reported once. Cross-references that follow the shift are not
  flagged; ones that do not are. A switch shows everything.
- **Scanned pages** (Q29): OCR is offered when Compare is pressed, for the comparison only; the
  files are not changed. Such differences are labelled **from OCR**, and typical confusions (0
  and O, 1 and l, rn and m) are grouped as **possible OCR error**, never hidden. OCR covers the
  app's five languages.
- **Every script is compared** (Q41): languages without spaces character by character,
  right-to-left text in its reading order, combined characters as one. Latin, Hindi, Japanese
  and Arabic are verified on corpus pair 11. Where text cannot be read reliably the result says
  **limited support**.
- One file per side (Q39).

### Text comparison: the view (D-64)

- **Document A | Document B side by side**, continuous scroll, the differences list on the
  right (Q32). Scrolling is synchronised **by content**, not by page number, so an inserted page
  does not throw the two sides out of step. Clicking an entry centres it on both sides. Bands
  connect each change across the gap. A switch turns the sync off. No inline redline pane.
- **Marks use colour and shape** (Q42): deleted = red with a strike-through, on the old side;
  inserted = green with an underline, on the new side; replaced = amber on both sides (old
  struck, new underlined); moved = blue on both sides with a band; changed figure = a blue
  frame. Colours through the swatch picker, saved in presets. A legend heads the list.
- The marks are drawn by the view. They are not comments, and Save review never writes them
  into either document.
- **The same review rules as the overlay** (Q43): all comment tools and menus in both windows,
  comments copied to the matching text on the other side, close-out tracking, filters, search,
  next and previous, the checked tick.

### Saving and outputs (D-65)

- **Save review** (Ctrl+S in a comparison tab, Q20): the reviewer's **new comments** are saved
  into Document A and Document B by the normal incremental save (rule 7), each window with its
  own unsaved mark. With several files per side, each file gets its own comments. Comparison
  highlights are never saved this way.
- **Save comparison…** creates or updates the **comparison file**, one standard PDF:

  |                         | PDF overlay (Q19)                                                 | Text comparison (Q33)                                                                                                    |
  | ----------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
  | Visible pages           | The vector overlay, one page per sheet; overlay notes as comments | Document B's pages with the changes as standard highlights, strike-outs and notes holding the old text ("was: 1,450.00") |
  | Inside, as attachments  | Document A, Document B (unchanged bytes), and the comparison data | Document A and the comparison data (Document B is the file's own pages; S31 settles how it is recovered byte for byte)   |
  | In any other PDF reader | An overlay drawing with comments, and two attachments             | The new revision with every change marked, and the old revision as an attachment                                         |
  | Reopened in Triya PDF   | The live comparison: pairing, alignment, options, ticks, notes    | The live comparison: both sides, marks, ticks, comments                                                                  |

  The comparison data is one small JSON attachment (pairing, alignment values, options, ignore
  zones, ticks, close-out states), and the file is tagged as ours through the PDF's standard
  place for application data (`/PieceInfo`). Everything is standard PDF (rule 6).

- In a reopened comparison file, Save review updates the copies inside it, and **Export
  Document A / Document B** writes them out as normal files.
- The Save dialog says in plain words that the file **contains both documents**, so that nobody
  shares it without meaning to share them.
- **Change register** (Q34): Excel and CSV with number, sheet or page, kind, old, new, percent,
  checked; it follows the list's filters. Optional **summary page** as the first page of the
  comparison file: file names, date, counts, legend and the settings used, ignore zones
  included.

### Speed, progress and acceptance (D-66)

- **Results arrive as they are ready** (Q40): the first sheet or page as soon as it is done,
  the rest in the background. The list fills in. What the user is looking at is worked on
  first. A progress indicator and Cancel are always there (rule 2).
- **Where the work runs** (rule 1): the Work worker reads and renders pages; a new **Compare
  worker** (our own code, no PDFium, like the Snap worker) does the alignment maths, difference
  detection and text matching, so a long comparison never blocks search or snapping. Tiles for
  the screen come from the Render worker as always.
- **Done means** (Q36): an automated **corpus acceptance** suite in CI plus the **owner's hand
  check** on real documents, which are never committed.

  | Check                                 | Proposed number (fixed in ADR-032 after the spikes)                                             |
  | ------------------------------------- | ----------------------------------------------------------------------------------------------- |
  | Differences found                     | Every difference in the two manifests, for all 25 pairs and the added pairs                     |
  | False reports                         | None on the control pages and chapters; none on the identical pair                              |
  | Alignment, vector pages               | Shift within 0.5 pt, scale within 0.05 %, rotation within 0.05° of the manifest values          |
  | Alignment, scans                      | Within 2 pixels at 150 dpi                                                                      |
  | First result                          | First sheet or page shown within 3 s of Compare on the reference machine                        |
  | Typical sheet (A1, CAD-like)          | Aligned and differences listed within 2 s per sheet; the dense A1 pair is measured and reported |
  | 500-page contract                     | Complete within 60 s                                                                            |
  | Main thread                           | No task over 100 ms, as everywhere                                                              |
  | Comparison file in Acrobat Reader etc | Opens without a warning; overlay black where the revisions agree; attachments open              |

### Not in M12 (agreed, Q39)

More than two revisions at once · inputs that are not PDFs · any AI · accepting, rejecting or
merging changes into a document · several files per side in a text comparison · a curtain
slider · an inline redline pane · a title-block reader · unit conversion · reporting
formatting-only changes · comparing comments as content · a folder picker · tablet and phone
layouts.

## Order of work

1. **M12-01** corpus first: the spikes need the realistic pairs.
2. **M12-02 … M12-06** spikes, one after the other. S27 comes first because every window of the
   result depends on it. M12-06 ends with **ADR-032**; the owner checks the two sample packs
   (vector overlay, comparison files) in Acrobat Reader and a second desktop PDF editor and
   accepts ADR-032. **Nothing is built before that.**
3. **M12-07 … M12-09** the base: worker, tab and input window, pairing.
4. **M12-10 … M12-16** the overlay, ending with the vector overlay.
5. **M12-17 … M12-19** the text comparison.
6. **M12-20 … M12-21** saving and outputs for both types.
7. Accepted optional items.
8. **M12-22 … M12-23** Help, release notes, acceptance, the owner pack. Version 1.1.0 is tagged
   by the owner after the hand check.

If a spike fails on something this plan promises (for example three live windows, or a vector
overlay that other readers draw correctly), the work stops there and the owner gets the options
(CLAUDE.md workflow).

## Questions for the owner

Each has a recommended answer; "yes to all recommendations" is a valid reply.

1. **Close-out states.** The app's comment status has Accepted, Rejected, Cancelled and
   Completed. **Recommended:** Addressed, Carried over and Changed differently all set the old
   comment to **Completed** (it is closed on the old revision) and add an automatic reply that
   names the outcome and the new file ("Carried over to RevB.pdf"). The Status and Replies
   columns of the CRS export then show both. The alternative is three new status names, which
   Acrobat Reader and other viewers would not understand.
2. **What the text comparison file shows in another reader.** Your first note said Document A;
   your answer to Q33 chose Document B's pages with the changes marked and the old text in
   notes. **Recommended:** Document B (Q33): a person without Triya PDF reads the new revision
   and sees exactly what changed.
3. **While it is being built.** **Recommended:** Compare is switched on in the beta site, PR
   previews and tests from M12-08, with a "Preview" tag, and switched **off in release builds**
   until M12-23. You can test each step, and a 1.0.x fix release cannot ship half a feature.
4. **Next and previous difference keys.** **Recommended:** F8 and Shift+F8, and hold `X` for
   Blink while the overlay has focus. (F3 is Find next, F7 is taken by the browser, and most
   other letters already pick a comment tool.)
5. **Optional items O1 … O5:** which ones? **Recommended:** O1 and O4.

## Risks

| Risk                                                                              | How it is handled                                                                                                                                                 |
| --------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Three live document windows do not fit the current single view                    | Spike S27 first; fallback: Document A and B as live windows and the overlay as a display-only window with its own notes layer                                     |
| The vector overlay draws wrongly or slowly in some reader                         | Spike S29 with three routes; it stays "beta" as a display mode; the image fallback keeps export working                                                           |
| Automatic alignment picks a wrong match on repetitive drawings (grids, schedules) | The "as is" check runs first; a confidence score; low confidence asks for points instead of guessing; manual alignment on every sheet                             |
| Too many false differences on scans                                               | Tolerance tied to sensitivity; minimum size; ignore zones; corpus pair 06 in the acceptance suite                                                                 |
| Reading order wrong on complex layouts                                            | Two extraction routes compared in S30; "limited support" notice; tables fall back to running text                                                                 |
| Header, renumbering and table logic hide a real change                            | Each is labelled experimental, has a switch to show everything, and reports what it folded together                                                               |
| Memory with two heavy drawings plus the overlay                                   | Measured in S27 and S29; analysis rasters are released per sheet; the Work worker respawn rule (§3.1) applies                                                     |
| Install size (OpenCV)                                                             | Only if S28 shows scans need it; on demand, never in the core precache; the size is reported to the owner in ADR-032                                              |
| A comparison file shared by mistake reveals both documents                        | Plain wording in the Save dialog; Export Overlay… gives a file without attachments                                                                                |
| The corpus is synthetic                                                           | Realistic pairs added in M12-01; the owner's hand check on real files is part of "done"                                                                           |
| Clean-room condition                                                              | Only published methods and permissive libraries; no other product's code, artwork or file format is used; the comparison file format is our own and is documented |
| M12 is large (23 tasks)                                                           | One task per thread, each mergeable on its own behind the build switch; the spikes can stop the plan early                                                        |
