# M9 — Help page with screenshots

> **Status (2026-11-07):** proposed, waiting for the owner's review.
> [ADR-026](../adr/026-m9-help-page.md) is Proposed.

Source: the owner's ask (2026-11-07): "Build a proper separate help page instead of floating help
window. It shall include necessary screenshots for easy human understanding." The owner
answered the planning questions upfront (same day; recorded at the end of this file), and also
said the **60 MB install budget is only a reference**, not a strict limit.

## Today

Help → Help (`help.help`) opens a modal dialog (`src/features/help/HelpPage.tsx`) with 22
sections of text only, about 13,000 characters in total (`help.section.*` in `en.json`). The
sections are long single paragraphs ("Reviewing comments" is 1,550 characters). There are no
pictures and no table of contents, the dialog covers the document, and you can't find text inside
it. The keyboard sheet (Help → Keyboard Shortcuts) is a separate dialog.

## What we build

### 1. A separate Help window

- **`help.html`** is a second Vite entry with its own small React tree (`src/help/`). It doesn't
  load EmbedPDF, the workers or the ribbon, so it opens instantly.
- **Help → Help**, **F1** (new; Ctrl+F1 stays "collapse ribbon") and the Help items on the start
  screen open it with
  `window.open('/help#<topic>', 'triya-help', 'popup,width=1100,height=820')`. The window
  name reuses one Help window, so pressing F1 again brings it to the front and jumps to the
  topic. In the installed PWA, Chrome opens it as its own app window. In a browser tab, it is a
  popup window. If the browser blocks it (it shouldn't, because it's a user gesture), the page
  opens in a new tab instead.
- **The floating Help dialog is removed** (`HelpPage.tsx`, `helpStore.ts`), along with its
  `help.section.*` strings once their content has moved.
- The page has its **own address**, `/help#topic-id`, which you can bookmark, share or print.
- Its layout is professional and documentation-style:
  - top: a header bar with the Triya PDF mark and name, "Help", a **search** box (it runs
    on Enter or the button, never as you type, rule 3), and Print;
  - left: a **table of contents** with chapters and topics, the current topic highlighted, and
    collapsible on narrow windows;
  - centre: the topic as a heading, a one-line summary, **numbered steps**, screenshots with
    captions and numbered callouts, tips, and the keyboard keys for this platform;
  - bottom of each topic: "Previous / Next" and "Related topics".
- **Theme:** it follows the app's light or dark choice (the same `pdftools.theme` key and
  `theme-boot.js`), and the screenshots stay light (see 3).
- **Accessible:** landmarks (`banner`, `navigation`, `main`, `search`), one `h1` per topic, a
  skip link, every image with alt text from i18n, visible focus, and screenshots that zoom
  (click opens the full-size image in a lightbox dialog that Esc closes). It passes axe, as the
  app does.
- **Print:** a print stylesheet hides the navigation and prints the topic, or the whole help with
  "Print all".
- **No network**, apart from loading its own same-origin files (rule 4). No document data ever
  reaches the help window. The two windows don't share state; the help only reads the theme key.

### 2. Works offline

- The service worker serves `help.html` for navigations to `/help` (it serves `index.html` for
  every navigation today) and precaches the help page, its script and its screenshots in the
  **background** group, after the first render (§9). F1 works offline once the "Ready offline"
  tick shows.
- `webp` joins `PRECACHE_EXTENSIONS`. The Cloudflare Worker's asset handling already serves
  `/help` from `help.html` (`html_handling: auto-trailing-slash`).
- **Install size: the 60 MB budget becomes a reference (owner, 2026-11-07).**
  `scripts/bundle-report.ts` keeps reporting the total and _warns_ above 60 MB instead of failing
  the build. ARCHITECTURE.md §9 says so. The 9 MB core budget is unchanged (it guards the first
  load). The screenshots are expected to add about 1.5–2.5 MB.

### 3. Screenshots generated from the real app

- **`npm run help:screenshots`** (`scripts/help-screenshots/`, a Playwright script, not part of
  CI) opens the built app in Chromium at **1366 × 800, light theme, English**, loads our
  **self-made sample PDFs** (a new `e2e/fixtures/help/` set: a two-page engineering drawing, a
  form and a report; rule 13), and walks through each shot's steps: it opens a tab, picks a
  tool, draws a comment, opens a dialog, and so on.
- Each shot is **cropped** to what it explains (a ribbon group, a pane, a dialog, a piece of the
  page). **Numbered callouts** (1, 2, 3 in the accent colour) and a highlight outline are drawn by
  an overlay the script injects around named elements. The numbers match the steps in the text.
- It writes **WebP** at quality 85, encoded inside Chromium with `canvas.toBlob('image/webp')`.
  This adds no new dependency: `sharp` bundles LGPL libvips, which rule 5 forbids. Each image is
  shown at 1× and stored at 2× pixels, so it stays sharp on high-DPI screens. Expect 20–60 KB
  each.
- The images go to `public/help/img/<topic>-<n>.webp`, with a generated `shots.json` (size, alt
  key). They are committed, so the help never depends on a build-time browser.
- **Keeping them current:** re-run the script after a UI change. The PR template's checklist gets
  "UI changed → re-run `npm run help:screenshots`". A unit test checks that every image the
  content names exists, has alt text and is listed in `shots.json`, and that no file is unused.
  A **@smoke e2e** test checks that every image loads in the help window.
- About **45 screenshots** (list below), light theme only. A dark-theme screenshot appears only
  in the Light and dark themes topic.

### 4. Content rewritten as task-oriented topics

Every topic is short: a one-line summary, then "To do X: 1. … 2. … 3. …" steps, then tips. The
strings live in a new **`src/i18n/help.en.json`** namespace (`help` namespace of i18next), not in
`en.json`, so the app's main bundle doesn't carry the help text. The i18n tests (completeness, the
pseudo-locale, no literals) cover it too. Keys in the text (`{{save}}`, `{{find}}` …) still come
from the keymap for this platform. The **Keyboard shortcuts** topic is generated from the keymap,
so it is always complete.

### 5. "?" links from the app (deep links)

`openHelp(topic?)` takes a topic id, and topic ids are stable (`comments.callouts`). In this
milestone, **F1 opens the topic for what you're doing**: the active ribbon tab's chapter, or the
open dialog's topic for the main dialogs (Sign Document, Security, Comment Styles Palette,
Flatten, Import Comments, OCR, Save Optimized, Print). Each of those dialogs also gets a small
**"?" button** in its title bar (Fluent `QuestionCircle`, accessible name "Help on …").
**Later, if wanted:** "?" in every pane and dialog.

## Risks

- **Screenshots drift** as the UI changes. Mitigations: the script makes regenerating them one
  command, and the PR checklist line reminds us to run it. They are not compared pixel by pixel
  in CI, because that would be flaky.
- **Popup blockers**: `window.open` from a click or key press is allowed by Chrome, Edge and
  Firefox. The fallback is a new tab.
- **The help and the app drift apart in features**: the acceptance checks the table of contents
  against the ribbon tabs (each tab has a chapter).
