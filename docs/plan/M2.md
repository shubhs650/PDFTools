> **Status (2026-09-26):** **Approved** by the owner on 2026-09-26, with every proposal in

Source: ARCHITECTURE.md §13 (Rev 0.4), M2 scope:

> Advanced search + find bar, bookmarks/thumbnails/attachments panes, print dialog + print-ready
> export, protected PDFs, signature pane, form filling, error-report endpoint.

Carried over from the M1 plan: text selection and copy with the text layer (M1-Q5) and File →

Every task is sized for **one session**. Each task ends with the CLAUDE.md "done" checks
(typecheck, lint, format, unit tests, relevant e2e, license gate, no new main-thread long tasks),
a `docs/PROGRESS.md` update, and commit messages that cite the D-xx / ADR ids listed under **Refs**.
New ribbon tabs appear only once they have a working command (M1-Q2): M2 brings the **Protect** tab
(Security Info, Unlock, Signatures); Redact stays hidden until M4.

**Why this order.** The two spikes come first because several M2 features depend on library
behavior nobody has measured yet (CLAUDE.md: spike before building on uncertain capabilities).
Protected PDFs come next because permission flags gate copy, print and form filling (rule 9).
Search is the milestone's biggest performance risk, so it starts early and in parallel. Panes share
one framework, so it is built once (M2-08) before the individual panes. Printing and the error
report are the most self-contained and go last, before the acceptance pass.

## M2-01 — Spike: viewer-side plugins and PDFium APIs (ADR-012)

> **Status (2026-09-26):** agent part done — _Works with workaround_,
> [ADR-012](../adr/012-m2-read-apis.md) (proposed; decision 5, layers, needs the owner). Text
> geometry, dense thumbnails and attachment reads must stay off the Render queue; layers can't be
> toggled with this PDFium. Consequences are folded into M2-04, M2-08, M2-10 and M2-11 below.

**Goal.** Before building panes and text selection, confirm what EmbedPDF 2.15.1 and PDFium offer
on the **hosted** Render worker, and what it costs, so no M2 pane hides an uninterruptible
Render-worker call on the main path (ADR-004) or a main-thread task > 100 ms (rule 1).

**Refs.** D-09, D-10, §5, ADR-004, ADR-011, ADR-001 B14.

**Depends on.** —

**Files likely touched.** `spikes/s10-read/*` (throwaway), `docs/adr/012-m2-read-apis.md`,
`package.json` (any new `@embedpdf/plugin-*`, pinned to exactly 2.15.1), `docs/plan/M2.md`
(adjust M2-04, M2-08, M2-10, M2-11).

**Questions to answer.**

1. **Text layer / selection:** does `plugin-selection` (or the engine's glyph/text-rect API) work
   over the hosted engine? Cost per page on the 2,000-page stand-in and a dense A0 sheet; does it
   queue behind tiles or block them? Do we instead take rects from the Work worker's text cache
   (M2-05)?
2. **Thumbnails:** `plugin-thumbnail` vs our own `PreviewLayer`-style renders at LOW priority; do
   thumbnail renders delay visible tiles (target: tile p95 within +10 % of baseline)?
3. **Bookmarks and links:** outline and link/destination APIs (`getBookmarks`, page link
   annotations, named destinations) and their cost on a deep outline.
4. **Attachments:** listing and reading embedded files (document-level `/EmbeddedFiles` and
   FileAttachment annotations) without copying large files through the main thread.
5. **Layers (optional content):** can PDFium list OCGs and render with a chosen visibility state?
   If not, what are the options (M2-Q8)?
6. Any plugin that fetches from the network, or that needs per-document `permissions` (never
   passed, ADR-011).

**Acceptance criteria.**

- ADR-012 records Works / Works with workaround / Blocker per question, with numbers, and the
  plugin list M2 will use. Every direct PDFium export used is listed (B14).
- Any conflict with ARCHITECTURE.md stops here with options for the owner.
- License gate passes; all `@embedpdf/*` still pinned exactly.

**Tests.** Spike Playwright page under the §10.1 CSP on self-made fixtures (outline 3 levels deep
with 500 entries, 20 attachments incl. one of 20 MB, two OCG layers, the 2,000-page stand-in),
recording long tasks, tile latency with and without thumbnail/text-layer load, and CSP/network
violations.

> the owner). Consequences are folded into M2-03, M2-14, M2-15 and M2-16 below.

**Goal.** Settle the library behavior behind protected PDFs, form filling and printing before

**Refs.** D-19, D-25, D-26, §7.10, §7.12, §7.13, §10.1, ADR-001 B4/B13/B14, ADR-005, rule 9.

**Questions to answer.**

1. **Passwords:** open with a user password in both workers (`FPDF_LoadMemDocument` password,
   EmbedPDF `openDocumentBuffer` password); wrong-password error code; R2–R6 handlers.
2. **Owner-password unlock:** what `FPDF_GetDocPermissions` / `FPDF_GetDocUserPermissions` return

## M2-03 — Protected PDFs: password prompt, permission gating, owner unlock

> **Status (2026-09-26):** done on branch `m2/03-protected`. Password prompt with retry and cancel
> (recovery and recent reopen ask again); one revision-aware permission map (`src/model/permissions.ts`)
> for the UI and the Render worker (fixes the R2 case); commands declare `requires: <capability>`
> and are disabled with "Not allowed by this document's security settings"; restrictions banner;
> Protect → Unlock in both workers (again after Work-worker reloads); the Protect tab appears with
> its first command (`shipped` flag in the command table). Passwords live only in memory: the Work
> client keeps them for respawn reloads, as it already did for the open password (M1-08); an e2e
> scan of IndexedDB, OPFS and web storage finds none.

> **From ADR-013:** code 4 for both missing and wrong passwords; `unlockOwnerPermissions` works on
> the open document (no reopen) — do it in both workers; re-read `FPDF_GetDocPermissions` after an
> unlock (EmbedPDF's document object keeps the old value); revision-aware permission map (R2's fill,
> assemble, accessibility and high-quality print follow bits 6, 4, 5, 3), also used by the save
> tracker (fixes its R2 case).

**Goal.** Open password-protected PDFs, honor permission flags everywhere, and unlock full access
with the owner password, like Adobe Reader (D-19). Never bypass restrictions (rule 9).

**Refs.** D-19, §7.12, ADR-011 decision 1, M2-Q7, rules 9 and 10.

**Depends on.** M2-02.

**Files likely touched.** `src/features/protect/{PasswordDialog.tsx,permissions.ts,PermissionBanner.tsx,unlock.ts}`,
`src/features/open/{openMachine.ts,openDocument.ts,errors.ts}`, `src/features/recovery/*`,
`src/features/recent/recent.ts`, `src/engine/{renderApi.ts,workApi.ts,workClient.ts}`,
`src/workers/{render.worker.ts,work.worker.ts}`, `src/app/commands/*`, `src/app/commands.ts`
(Protect tab visible), `src/i18n/en.json`.

**Acceptance criteria.**

- Opening an encrypted file with a user password shows a password dialog (masked input,
  accessible name, retry on wrong password with a localized message, Cancel closes the tab). The
  password reaches both workers and is never stored (M2-Q7).
- Files with an owner password only open directly with restricted permissions.
- Every command that the permission flags forbid (print, high-quality print, copy, fill forms,
  annotate, modify, assemble) is disabled with a reason ("Restricted by the document's security
  settings") via the M1 disabled-reason mechanism; a banner above the document explains it.
- **Protect → Unlock with Owner Password** re-evaluates permissions for the session; the banner
  and commands update. Wrong owner password changes nothing.
- Recovery and recent-file reopen of an encrypted document ask for the password again.
- Ctrl+S on an encrypted file still produces the ADR-005 narrow tail (R, P and method unchanged).

**Tests.** Unit: permission-bit → command-state mapping (every bit, R2–R6 semantics), password
state machine. E2E: user-password file (wrong then right), owner-only restricted file (commands
disabled with reasons, banner, axe-clean), owner unlock, recovery of an encrypted doc re-prompts,
a test that scans IndexedDB/OPFS after the flow and finds no password.

## M2-05 — Search core in the Work worker

> **Status (2026-09-26):** done on branch `m2/05-search`. `search` / `searchContext` / `hitRects`
> RPCs on the Work worker (interactive priority, a checkpoint per page), session text cache per
> document, `SearchSession` on the main thread (a new search cancels the old one; stale batches are
> dropped). Batches go through a new unthrottled, ordered `ctx.stream()`: the M1 progress channel
> keeps only the latest value and would have lost hits. Measured on the 2,000-page stand-in (e2e
> build, perf guard): cold first hit 53–176 ms and complete 5.1–5.7 s; warm rare term 13 ms; a
> 910k-hit regex in 87 ms with 5,000 hits in context and an exact total; 0 long tasks. **Finding:**
> this PDFium build counts a non-BMP character as two chars (UTF-16 code units), unlike ADR-006's
> note; rectangles use `FPDFText_GetCharIndexFromTextIndex`, which is right either way.

**Goal.** Port the S5 search into the Work worker as the one search engine for Quick Find and
Advanced Search (D-08, D-10, ADR-006).

**Refs.** D-08, D-10, §6, ADR-006 decisions 1–2, ADR-004, rules 1–3.

**Depends on.** — (M1 Work worker and scheduler).

**Files likely touched.** `src/workers/work/{search.ts,searchCore.ts,textCache.ts,rects.ts}`,
`src/workers/work.worker.ts`, `src/engine/{workApi.ts,workClient.ts}`, `tests/work/search*.test.ts`.

**Acceptance criteria.**

- `search` RPC: query + options (match case, whole word, wildcards, regex) compiled to JS `RegExp`
  (S5 `search-core.ts`); runs at interactive priority; pages in viewport order (visible, onward,
  wrapping); results stream in batches ≤ every 50 ms with a search id; a new search cancels the old
  one; stale batches are dropped.
- At most 5,000 hits streamed with context, then per-page counts only; exact total; a `context`
  RPC returns hits for a page range on demand (ADR-006 decision 2).
- `rects` RPC returns highlight rectangles per hit, with correct string-index ↔ char-index
  mapping for non-BMP characters (`FPDFText_GetTextIndexFromCharIndex`).
- Invalid regex returns a localized error code, not an exception message (rule 10).
- Text cache is session-only, released on eviction or respawn (ADR-004).

**Tests.** Unit: the 10 S5 tests ported, plus non-BMP mapping, 5,000 cap with exact count, cancel
between pages, stale-id drop (real PDFium in Node like M1-17). E2E via test hook: search the
2,000-page stand-in, first hit < 1 s and complete < 15 s, 0 long tasks.

## M2-06 — Background text indexing

> **Status (2026-09-26):** done on branch `m2/06-indexing`. `indexText` job at background priority (viewport order, yields at every page, parked during save verification), paused while the user scrolls or zooms (`activity` RPC, throttled on the main thread); searches take visible, then cached, then other pages. Measured: during a 3 s scroll at 900 px/s only 35–72 pages were indexed (1,000+ unpaused), tiles unchanged, 0 long tasks; afterwards a rare term far away: first hit 12 ms.

**Goal.** Build each document's text index in the background after open, so rare terms anywhere
get first hits in < 1 s (ADR-006 decision 3, §6).

**Refs.** §6, ADR-006 decisions 3–4, ADR-004 decision 4, M1-08 scheduler.

**Depends on.** M2-05.

**Files likely touched.** `src/workers/work/{indexer.ts,scheduler.ts}`, `src/engine/workClient.ts`,
`src/features/view/controller.ts` (scroll/zoom activity signal), `src/features/search/indexing.ts`.

**Acceptance criteria.**

- After first render, the Work worker extracts all pages at background priority in viewport order.
- It yields to searches (a search mid-index searches cached pages first, then continues), backs
  off while the user scrolls or zooms, and parks during saves and save verification.
- Tail refreshes invalidate only affected pages; closing a tab cancels its indexing.
- No persistent text cache (ADR-006 decision 4); the privacy page needs no new entry.

**Tests.** Unit: scheduler preemption and back-off with fake timers. Perf scenario: open the
2,000-page stand-in, auto-scroll at 900 px/s while indexing — 0 long tasks, tile p95 within
+15 % of the no-indexing baseline; after indexing, rare-term search on page 1,000 first hit
< 1 s.
