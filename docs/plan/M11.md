## What we found

### 1. OCR text cannot be selected until the file is reopened: root cause found

Search and selection read the text from different places:

- **Search** asks the Work worker, whose copy of the document is refreshed after every change
  (`syncLive` → `setLive`, which also drops its search cache). So Find sees the OCR text at once.
- **Selection** uses EmbedPDF's selection plugin on the main thread, which **caches each page's
  text geometry** (glyph boxes) the first time the page is shown (`getOrLoadGeometry`, up to 30
  pages). For a scanned page that cache entry says "no text".
- After a page operation, `afterChange` (`src/features/pages/pageOps.ts`) clears the cached
  geometry only for pages whose **identity** changed or that the change lists as **content
  pages**. `contentPages()` lists pages only for Flatten. The OCR layer is applied as an
  `objects` change (the comment-transfer route): the pages keep their object numbers and no
  content pages are listed, so **the stale "no text" geometry stays** until the document is
  reopened. Saving does not touch it either, which is why the user still saw it after Ctrl+S.
  Undoing the OCR step has the mirror bug (the text geometry would stay after the layer is
  gone).

Fix (M11-01): the OCR change names the pages whose text it changed, so their geometry is
evicted and the visible ones are refreshed, on apply, undo and redo. We also audit every other
route that changes page text without changing page identity.

### 2. Fonts

Text boxes, typewriters and callouts offer **three families** (Helvetica, Times, Courier, with
bold and italic): the PDF standard fonts. They are the only fonts PDFium can draw an annotation
appearance with (`EPDFAnnot_GenerateAppearance` reads `/DA`), which is why §7.1 says "no custom
appearance-stream generation" apart from two narrow exceptions (Attach File's paperclip,
ADR-022; text colours, ADR-024). Form fields use the same three. Typed signatures already use
three bundled handwriting fonts (OFL-1.1), drawn as images.

A real font library therefore needs three things: **font files we ship** (offline, from our own
origin: rule 4, so never Google's servers at runtime), a way to **draw text comments with an
embedded font** in a standard appearance stream (rule 6), and a **picker** that stays short.
What we propose is under [Fonts](#fonts-d-52) below; the drawing route is uncertain enough that a
spike (S26) comes first.

### 4. Comments cannot be picked in Hand or Select Text

**By design today, and we agree it should change.** `DocumentView.tsx` locks every annotation
(`LockModeType.All`) unless the tool is Select or Select Comments (decision from M3-05, so that a
drag in Select Text always selects text). The page menu offers Hand, Select Text and Select
Comments, but **not Select** (the default tool that does both), so a user who picks a tool there
easily ends up in a mode where comments ignore clicks. Image stamps and visual signatures are
comments, so they are covered by the same fix. Images that are part of the page content are not
comments; copying them is optional item O6.

### 5. Obvious features we are missing

We went through the ribbon, the menus and a day of typical engineering use (open several
drawings, mark up, measure, extract, save, reopen tomorrow) against what Acrobat Reader,
PDF-XChange Editor and browsers' own PDF viewers do. The gaps that matter most are listed as
optional items **O1–O9** below, for the owner to accept or decline, as in M10. Two small gaps
are folded into the tasks because they belong to the owner's asks: the page menu's missing
**Select** (M11-06) and **Reopen closed tab** on the tab menu (M11-05).

## Design

### File tabs (D-50)

A rough CSS-only preview of the selected tab, the + button and the hover card (injected into the
current build, not the final design) is in the shared folder `m11-plan/preview/`, light and dark.

- **Selected tab:** filled with the theme's **accent** (`--color-brand`: Blue, Teal, Indigo or
  Graphite), white semibold name, white × and white unsaved dot, 8 px rounded top corners, so it
  reads as a raised tab joined to the document. White on every accent passes AA (5.2 : 1 blue,
  5.5 teal, 6.3 indigo, 7.6 graphite). In **dark**, the filled indigo and graphite are below
  3 : 1 against the dark strip (2.8 and 2.4), so the selected tab also gets a 2 px line in the
  light accent along its bottom edge, which is 3 : 1 or more in every case (WCAG 1.4.11); the
  state never relies on the fill alone (bold name, line, `aria-selected`). Other tabs: no
  dividers, a soft hover tint, × shown on hover and focus (and always on the selected tab), the
  unsaved dot in the accent. **Forced colours:** Highlight/HighlightText. The fix for the CSS
  order bug comes with it and a test checks the selected tab's computed background.
- **Hover card** (instead of a plain tooltip, like PDF-XChange's): after 500 ms over a tab, or
  when a tab gets keyboard focus and stays there for 800 ms. It shows the **page 1 thumbnail**
  (from the existing thumbnail renders, Render worker: rule 1; shimmer placeholder until ready),
  the **full file name** (wrapped, never cut), **where it came from** instead of a path ("Opened
  from this device", "Dropped onto Triya PDF", "New document, not saved yet", "Recovered after a
  crash", "Saved as … on this device"), **pages · file size · file's last modified time** (`Intl`),
  and status chips: Unsaved changes, Read-only, Protected, Signed. It follows WCAG 1.4.13: it
  stays while the pointer is on the tab or the card, Esc closes it, it never covers the tab. The
  tab's accessible description gives the same text to screen readers. The card never appears
  while a tab is being dragged.
- **+ button** right after the last tab (it moves with the tabs, and sits before the overflow
  menu when the row scrolls): opens a file (the same Open as Ctrl+O), tooltip "Open a file
  (Ctrl+O)". See Q4 for the alternative (a small menu). Double-clicking the empty part of the
  strip opens a file too, as in Chrome.
- **Drag to reorder, Chrome-like:** press on a tab and move 4 px: the tab lifts (shadow) and
  follows the pointer along the strip, the others slide out of its way (150 ms transform, none
  under reduced motion); release drops it there, Esc puts it back. The strip auto-scrolls when
  the pointer is near either end of a scrolling row. Works with mouse, pen and touch (pointer
  events, pointer capture). Only `transform` changes during the drag (no layout per frame,
  rule 1). **Keyboard and single-pointer alternatives** (WCAG 2.1.1, 2.5.7): Ctrl+Shift+Left /
  Right (and Ctrl+Shift+PageUp / PageDown in the installed app) moves the focused tab; the tab
  menu has Move Left / Move Right; a live region says "Moved to position 2 of 4". Dragging a tab
  out of the window does nothing (one window, as today). **Middle-click** closes a tab, as in
  Chrome.
- **Tab right-click menu** (also Shift+F10 / Menu key on a focused tab):

  | Item                                                                | Notes                                                                                                                                                                                  |
  | ------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
  | Save · Save As…                                                     | Existing commands, for this tab's document.                                                                                                                                            |
  | Close · Close Other Tabs · Close Tabs to the Right · Close All Tabs | Unsaved documents ask one by one, as Close does today.                                                                                                                                 |
  | Reopen Closed Tab                                                   | The last closed tab (this session), from its saved file handle, as Recent files does. Shortcut Ctrl+Shift+T where the browser lets us have it (the installed app), else from the menu. |
  | Move Left · Move Right · Sort Tabs by Name                          | The keyboard and single-pointer way to reorder; Sort is natural order ("Sheet 2" before "Sheet 10").                                                                                   |
  | Copy File Name                                                      | The full name to the clipboard (no path exists to copy).                                                                                                                               |
  | Rename File…                                                        | **Only where the browser can rename the original file in place** (File System Access `move()`, write permission granted), checked in the task; hidden elsewhere, never a fake rename.  |
  | Document Properties…                                                | File → Properties for this document.                                                                                                                                                   |

  The empty part of the strip has its own menu: Open…, Create Blank PDF…, Reopen Closed Tab,
  Close All Tabs. **Not offered**, because a web app cannot do them: Open Containing Folder,
  Copy Full File Name (path), Copy File, Move To Trash, Move File, Move Tab to New Window or tab
  groups. Duplicate Tab (two views of one document) is a bigger feature, left for later.

### Comments in every pointer mode (D-51)

As in Acrobat and PDF-XChange, a comment (including image stamps, visual signatures and file
attachments) can be picked in **Select, Hand and Select Text**, not only in Select and
Select Comments:

- **Hand:** a click on a comment selects it (handles, Properties pane, right-click menu); a drag
  that starts **on** a comment moves it (unless it is locked or the document forbids changes,
  rule 9); a drag anywhere else pans, as now. Double-click edits a text comment or opens a sticky
  note, as in Select. See Q5.
- **Select Text:** a click on a comment selects it. On a **text markup** (highlight, underline,
  strikeout, squiggly) a press that turns into a drag **selects text** (so highlighted text can
  still be copied) and a click without a drag selects the markup. Over any other comment a drag
  moves it. See Q6.
- Form fields keep their fill-in behaviour in every mode except Select Fields (unchanged); links
  still follow on click when no comment is on top.
- The pointer shows the move cursor over a selectable comment in all three modes, and the Tab
  key's "next comment" works in all of them.
- **Page menu:** gains **Select** (first of the tools) and shows the current tool checked
  (`menuitemradio`), so the menu never leaves the user unsure which mode they are in.

### Fonts (D-52)

**Where the fonts come from.** Every font is from the **Google Fonts library** and under
**OFL-1.1 or Apache-2.0** (both in our allowlist, rule 5; checked per file by the license check;
Google Fonts' few UFL fonts are excluded). The files are **shipped with the app and served from
our own origin**, never fetched from Google at runtime (rule 4: no CDNs, and Google would see
every user's IP address). They are precached in the background after the first visit, so they
work offline, like the CJK rendering fonts today. See Q1 for the on-demand alternative.

**The proposed library** (Q2): about 26 families, chosen for engineering documents and for the
five languages we support (English, Spanish and French in every Latin family; Hindi; Chinese),
with every face that the family has among Regular, Bold, Italic and Bold Italic:

| Group                           | Families                                                                                                                  | Why                                                                                                                                                           |
| ------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Standard (kept, not embedded)   | Helvetica, Times, Courier                                                                                                 | Every PDF viewer has them; smallest files. Still the defaults (Helvetica for text boxes, Courier for the typewriter).                                         |
| Office-compatible (same widths) | **Arimo** (as Arial), **Tinos** (as Times New Roman), **Cousine** (as Courier New), **Carlito** (as Calibri)              | Text set in our app takes the same space as in the Word and Excel files engineers work with. Carlito only if it is in the library under OFL (checked in S26). |
| Sans-serif                      | Inter (our UI font), Roboto, Open Sans, Noto Sans, IBM Plex Sans, Atkinson Hyperlegible                                   | Clean, very readable at small sizes on drawings; Atkinson Hyperlegible was designed for low vision.                                                           |
| Narrow                          | Roboto Condensed, Barlow Condensed                                                                                        | Long notes in title blocks, tables and tight callouts.                                                                                                        |
| Technical                       | B612 (designed for Airbus cockpit displays), Overpass (highway-sign lettering)                                            | Legibility-first lettering that suits drawings and signage.                                                                                                   |
| Serif                           | Noto Serif, Source Serif 4                                                                                                | Reports and letters.                                                                                                                                          |
| Monospace                       | Roboto Mono, JetBrains Mono, IBM Plex Mono                                                                                | Tag numbers, codes, aligned values.                                                                                                                           |
| Handwriting                     | Architects Daughter (architectural hand lettering), Caveat (already bundled for signatures), Kalam (Latin and Devanagari) | Informal review notes.                                                                                                                                        |
| Hindi (Devanagari)              | Noto Sans Devanagari, Noto Serif Devanagari (plus Kalam)                                                                  | Hindi text in comments.                                                                                                                                       |
| Chinese (Simplified)            | Noto Sans SC (Regular; the file we already ship for rendering, so no extra download; bold drawn with a stroke)            | Chinese text in comments.                                                                                                                                     |

Estimated size: **about 8–10 MB** more in the background precache (the core 9 MB does not
grow); measured in S26 with the real files. The install is 60.5 MB today, a reference and not a
limit. **Owner's answer (Q1): ship all of it with the app** (option A); S26 and M11-07 report the
measured size.

**Missing characters.** When the text has characters the chosen font lacks (Hindi typed in
Roboto, a Chinese name in Arimo), those characters fall back by script to Noto Sans Devanagari
or Noto Sans SC, on screen and in the saved appearance, instead of empty boxes.

**The picker.** One font list wherever a text comment's font is chosen: the Properties pane, tool
defaults, the Comment Styles window and the text menu's Text Style. It is grouped as in the
table, each name drawn in its own face, **Recently used** (5) on top, type-ahead to jump to a
name (a short local list: not a document search, rule 3). Previews load only when the list
opens.

**How a comment is drawn (spike S26 decides the route).** The text stays a standard FreeText
annotation (`/Contents`, `/DA`, `/DS`, `/RC` with the family name), so any viewer lists and
reads it; its **appearance stream** is ours, with the used characters of the font **embedded as
a subset** (CIDFontType2, Identity-H, with ToUnicode, as our OCR text layer already does), so
Acrobat, PDF-XChange and every other viewer show it exactly, and flattening keeps the text
searchable. The spike compares:

- **Route R1, PDFium page objects:** `FPDFText_LoadFont` and text objects on a scratch page,
  turned into the appearance with `EPDFAnnot_SetAppearanceFromPage` (the call ADR-024 already
  uses for text colours). Little new code, but PDFium does not **shape** text (Devanagari
  conjuncts and vowel signs come out wrong) and embeds whole font files (larger PDFs).
- **Route R2, our object layer:** HarfBuzz (`harfbuzzjs`, MIT) shapes the text and subsets the
  font; the Work worker writes the appearance stream and the font objects. Correct for every
  script and small files; more code. Our expectation is R2, or R1 for Latin with R2 for
  Devanagari.

All of it runs in a worker (rule 1). The spike also checks: line wrapping and alignment matching
the on-page editor, rotation, text and border colours (ADR-024), re-applying our appearance
after EmbedPDF regenerates it on a move or resize, Ctrl+S's narrow tail with the font objects,
and what **Acrobat and PDF-XChange do when the comment is edited there**: they redraw it with
their own fonts if ours is not installed, which is normal for any FreeText and is said in Help;
just displaying it keeps our appearance. This is the **third exception** to "no custom
appearance streams" (§7.1) and needs the owner's interop check (Acrobat Reader, PDF-XChange).

**Scope (Q3):** text boxes, typewriters and callouts (and their defaults and styles). **Form
fields keep the standard fonts** in M11: a viewer fills a field with the font in the form's
`/DR`, and a subset font there cannot draw characters the user types later, so form fonts need
whole embedded files and their own interop testing.

**How the two items we had put off are built:**

- **O5 system fonts** comes last among the optional items, after the font library (M11-07) and
  its interop check, on the same appearance writer. Chromium's `queryLocalFonts()` runs only on
  a click in the font list ("Show fonts on this computer…"), behind the browser's permission
  prompt; nothing is read until then and nothing leaves the device. A font is usable only when
  its OS/2 embedding flags allow embedding (installable or editable; preview-and-print fonts
  embed for viewing only, as Acrobat does); restricted fonts are listed but disabled with the
  reason. The chosen font's family name is remembered on the device (Recently used); the file
  itself is never stored. Other browsers do not show the entry.
- **O9 crop** writes only `/CropBox` per page (the content is untouched), as one undo step
  through the existing page operations, so other viewers honour it and Remove Crop restores the
  page; measurement scales (Viewport, D-14) keep their page coordinates, so measurements stay
  correct on a cropped page (tested).

Considered and not proposed: dark page colours (pages stay white, D-42), headers/footers,
watermarks and Bates numbers (Rev 2+, §14), revision compare (parked, rule 14), a second window
for a tab (one window today).

## Risks

- **Fonts in appearance streams** are new ground for us: shaping, subsetting and interop. Spike
  S26 comes first and the owner's interop check gates M11-07; the fallback is Latin families
  first and Devanagari/Chinese after.
- **EmbedPDF regenerates FreeText appearances** after edits; our appearance must be re-applied
  each time (the same hook as ADR-024's colours), or a moved comment would fall back to
  Helvetica. Tested on move, resize, rotate, style change, undo and redo.
- **Comments in Hand and Select Text** change a decision from M3-05: some e2e tests that drag
  over comments to select text or pan will change behaviour. The full suite runs on M11-06.
- **Drag reorder** must not fight the existing tab keyboard model, the overflow menu or the
  file drop overlay; dropping files onto the strip still opens them.
- **Rename File** depends on a Chromium API for local files; if it is not reliable, the item is
  left out rather than faked.
- **Install size** grows by the font library (Q1); measured in S26 and M11-07.
