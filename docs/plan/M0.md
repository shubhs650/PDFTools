# M0 — Spikes (de-risk before building UI)

Source: ARCHITECTURE.md §13. The owner's session-1 answers are recorded in
[ADR-001](../adr/001-session-1-clarifications.md).

Each spike ends with a short ADR (`docs/adr/NNN-sN-<topic>.md`, from the
[template](../adr/000-template.md)) whose outcome is one of **Works / Works with workaround /
Blocker**. Spike code lives in `spikes/sN-<topic>/`. It is throwaway, never imported by `src/`,
and not shipped. Any dependency added for a spike must pass `npm run licenses`.

## Ground rules for all spikes

- **Heavy-file targets are measured, not gated.** The 500 MB contract, dense A0 drawings and
  P&IDs are tested by the owner with local files (ADR-001 B15). The agent provides the harness
  and a results table. Acceptance limits for those files may be relaxed (B4, B9, B12). Memory is
  reported but not limited (B10).
- **Corpus:** public-domain or self-made PDFs only, fetched by script into `corpus/files/`
  (git-ignored). Copyrighted standards (ASME, ISO) are never used. Primary contract-profile file:
  the **Federal Acquisition Regulation** (US government work, public domain, about 2,000 pages).
  Small feature files are self-made (drawn in-app or created by the spike itself) or taken from
  public test suites whose licenses allow use (e.g. pdf.js test PDFs, checked per file).
- **No network:** every spike runs with the PDFium WASM file and fonts self-hosted. EmbedPDF's
  defaults point at jsDelivr (`cdn.jsdelivr.net/npm/@embedpdf/pdfium@…/pdfium.wasm` and
  `…/@embedpdf/fonts-*`), so every spike must override both (CLAUDE.md rule 4).
- **Interop checks** in Acrobat Reader and PDF-XChange are run by the owner on Windows from a
  checklist the agent prepares (B16).
- **Main-thread health:** any spike with UI records `PerformanceObserver('longtask')` entries.

## EmbedPDF capability snapshot (v2.15.1, read from the published npm packages)

All `@embedpdf/*` packages checked are MIT. Findings that shape the spikes:

- **Annotation tools** (`plugin-annotation` default tools): `highlight`, `underline`,
  `strikeout`, `squiggly`, `textComment` (sticky note), `freeText` (text box / typewriter),
  `freeTextCallout`, `line`, `lineArrow`, `polyline`, `polygon`, `square`, `circle`, `ink`,
  `inkHighlighter`, `stamp`, `insertText` / `replaceText` (Caret), `link`. The models also
  cover FileAttachment, Widget and Redact annotations. Square, circle and polygon support
  `cloudyBorderIntensity`, which is how we get the **cloud** markup.
- **How these map to ARCHITECTURE §7.1 (per ADR-001 B7):** every §7.1 type has an EmbedPDF
  equivalent **except the measurement types**. Those are covered by S2. Rev 0 ships the EmbedPDF
  set, with no custom appearance-stream code.
- **Redaction** (`plugin-redaction` + engine): marquee (area) and text-selection marking, a
  pending list, and `redactTextInRects`, `applyRedaction`, `applyAllRedactions` ("removes
  content, flattens overlay, deletes annotation"). This is the M4 engine (B8).
- **Saving:** the engine API exposes `saveAsCopy(doc) → ArrayBuffer` with no incremental
  option. The bundled PDFium exports `FPDF_SaveAsCopy(doc, writer, flags)` and
  `FPDF_SaveWithVersion`, so the incremental flag is probably reachable by calling PDFium
  directly (S1).
- **Workers:** `WebWorkerEngine`, `PdfiumEngine` and `createPdfiumEngine` are exported (S3).
- **Fonts:** CJK, Arabic, Hebrew and Latin fallback fonts come as `@embedpdf/fonts-*`
  packages, licensed **OFL-1.1**. That license is not on the allowlist yet; the owner needs to
  decide (see PROGRESS.md).

## Suggested order

**S8 → S3** (engine running in workers under the real CSP, with no CDN), then **S1 → S5 → S2 → S7
→ S4 → S6**. S6 is independent and can be done at any time.

## S1 — Incremental save + full-rewrite save through EmbedPDF/PDFium

**Goal.** Prove that the Render worker can (a) append an **incremental update** to the
original bytes for Ctrl+S, and (b) produce a **full rewrite** for Save Optimized and redaction.
Both must preserve annotations, form values, encryption and existing signatures as §4.2 and D-06
require.

**Method.**

1. Build a minimal worker harness in `spikes/s1-save/`. It loads EmbedPDF's PDFium engine from a
   self-hosted `pdfium.wasm`.
2. Test inputs, all self-made or public:
   - a plain text PDF;
   - a PDF that already carries annotations;
   - an AcroForm;
   - a PDF encrypted with an owner password and restricted permissions;
   - a PDF with a digital signature. Use a self-made one signed with a throwaway test certificate.
3. Add one annotation of **every EmbedPDF tool type**, plus 100 markups for the timing test.
4. Save three ways:
   - `engine.saveAsCopy()`, recording which flags it uses;
   - a direct `FPDF_SaveAsCopy` call with `FPDF_INCREMENTAL`;
   - a direct `FPDF_SaveAsCopy` call with `FPDF_NO_INCREMENTAL`.
5. Check the incremental output:
   - the original bytes are an exact prefix of it;
   - a new xref/trailer section is appended;
   - `qpdf --check` passes (external CLI, Apache-2.0, not a project dependency);
   - the signature's byte-range hash still matches its CMS digest (small PKI.js script);
   - an encrypted input stays encrypted with the same permissions.
6. Check the full rewrite: file validity, size compared with the original, and whether unused
   objects are dropped ("garbage-collected, compressed" per §4.2).
7. Time these on a small file (under 20 MB) and a large file (owner's local file):
   - the save call;
   - an FSA `createWritable({ keepExistingData: true })` append;
   - an OPFS write of just the incremental tail (the basis for the B11 recovery design).
8. Produce an **interop pack**: the saved files, plus a checklist for the owner to open, edit and
   re-save in Acrobat Reader and PDF-XChange. This covers D-03 round-trip for the EmbedPDF
   annotation set.

**Success criteria.**

- The incremental save leaves the original bytes untouched as a prefix and passes `qpdf --check`.
- The test signature is still "unchanged since signing" after an incremental save.
- An encrypted input remains encrypted with the same permissions after both save modes.
- On the small file, an incremental save with 100 markups takes **under 1 s** end to end,
  including the FSA write. The large-file number is reported, not gated (B12).
- The full rewrite produces a valid file, and we know whether PDFium drops unreferenced objects.
- The owner's interop checklist shows that every EmbedPDF annotation type renders, and survives
  an edit, in both viewers.

**If it fails.**

- _`saveAsCopy` has no flags:_ call `FPDF_SaveAsCopy` directly from the Render worker (B14) and
  wrap it in our `renderClient` API.
- _PDFium's incremental save rewrites or reorders earlier bytes, or breaks signatures:_ write a
  narrow incremental-update writer. It serializes only changed or new objects, plus a new xref
  and trailer. This is a significant change and needs an ADR and an owner decision.
- _The full rewrite doesn't garbage-collect:_ ship Save Optimized as PDFium's non-incremental
  rewrite and document the size behavior. Evaluate a permissive object-level GC pass separately.
- _An annotation type fails interop in a viewer:_ record it in the ADR, then either hide that
  tool for Rev 0 or mark it "limited interop". The owner decides which.

## S2 — Measure/Viewport dictionaries, read back in Acrobat Reader & PDF-XChange

**Goal.** Find out whether we can write ISO 32000 measurement structures and whether both
target viewers honor them. That means a `/Measure` (RL) dictionary on line, polyline and polygon
annotations, the right `/IT` (`LineDimension`, `PolyLineDimension`, `PolygonDimension`), and page
`/VP` viewport arrays with their own scale. We also need to read measurements created by those
viewers (§7.4, D-14).

**Method.**

1. List the write APIs available. EmbedPDF's annotation model has **no measurement fields**, and
   PDFium's public API has no general nested-dictionary writer, so the likely route is a narrow
   writer in the Render worker. It would rewrite the annotation and page objects in an
   incremental update, building on S1.
2. Prototype on a self-made A1 sheet:
   - a page default scale of 1:100;
   - a "Detail A" viewport at 1:5;
   - a distance, a perimeter and an area measurement inside and outside the viewport;
   - one measurement that spans both regions.
3. The owner opens the file in Acrobat Reader and PDF-XChange and records, for each viewer:
   - whether the measurement shows as a measurement;
   - the displayed value and units;
   - whether the viewport scale is used;
   - whether editing preserves the data.
4. Reverse direction: the owner creates the same measurements in both viewers and saves. We
   parse them back into our `ScaleViewport` and measurement model.
5. Separately, find out how the measured-value label is drawn. Viewers render from the appearance
   stream. With no custom appearance-stream code (B7), the label may need `/Cap` + `/Contents`
   on lines, or a companion FreeText annotation.

**Success criteria.**

- Both viewers show values matching ours to display precision for distance, perimeter and area.
- Viewport scale is respected by at least PDF-XChange. Acrobat's behavior is documented either way.
- Measurements created in both viewers parse correctly into our model, including scale and units.
- A label strategy that renders in both viewers without custom appearance-stream code is chosen,
  or the need for one is escalated to the owner.

**If it fails.**

- _Viewers ignore our dictionaries:_ still write the standard structures for future
  compatibility. Show the value through the label strategy so it renders everywhere. Document
  "measurement data readable by PDFTools; visual value in other viewers".
- _Writing nested dictionaries is impossible without our own object writer, and that is too
  costly:_ raise with the owner. Options are a scoped writer (S1 fallback), or storing
  measurement metadata in a standard-compliant private key alongside the standard annotation.
  The second option weakens D-03 and needs an ADR.
- _Labels need custom appearance streams:_ raise with the owner, because this conflicts with B7.

## S3 — Two EmbedPDF/PDFium engine instances in two workers; memory with a 500 MB contract

**Goal.** Confirm the D-10 process model:

- the Render worker is EmbedPDF's engine, driving the headless plugins;
- the Work worker is a second, independent PDFium instance behind our own typed RPC;
- the two run concurrently without contention.

Measure memory and tile behavior on heavy files.

**Method.**

1. Build a spike app in `spikes/s3-two-engines/`:
   - the Render worker uses EmbedPDF's worker engine, with a custom worker URL and the WASM file
     self-hosted;
   - the Work worker calls `createPdfiumEngine` inside our own worker module.
2. Load the same document into both: transfer the `ArrayBuffer` to one worker and copy it to the
   other.
3. Run a long Work job (full-text extraction) while scrolling and zooming in the Render worker.
   Record whether tile latency degrades.
4. Record for each worker: the WASM `memory.buffer.byteLength` after opening, after closing, and
   after terminating and respawning the worker. WASM memory never shrinks, so check that respawn
   reclaims it.
5. Also record total tab memory from Chrome's task manager, or
   `performance.measureUserAgentSpecificMemory()`, which needs cross-origin isolation; note
   whether COOP/COEP headers would be acceptable.
6. Measure tile cancellation and deep zoom:
   - whether an in-flight EmbedPDF render can be aborted;
   - how long a 256 px tile takes at 100 %, 800 % and 6400 % on a dense A0 page;
   - whether PDFium progressive rendering (`FPDF_RenderPageBitmap_Start` with pause) is used or
     reachable.
7. Inputs: the FAR for the contract profile. The owner runs the **500 MB contract** and a
   **dense A0 drawing** from local files.

**Success criteria.**

- Two instances load and work at the same time with no shared-state errors.
- Work-worker jobs do not block Render-worker tiles; any tile-latency increase is recorded.
- No main-thread long task over 100 ms during open, scroll or zoom on the FAR.
- A memory table exists: per worker, per document, and before and after respawn. There is no
  limit (B10).
- Tile timings at the three zoom levels are recorded for the owner's drawing (relaxed targets,
  B9), and it is clear whether in-flight renders can be cancelled.

**If it fails.**

- _EmbedPDF can't host a second instance (module-level singletons):_ load the second PDFium WASM
  module directly in a plain worker with our own thin wrapper, keeping EmbedPDF only in the
  Render worker.
- _Contention or memory is unacceptable later:_ start the Work worker lazily, load only the page
  ranges it needs, evict idle documents by respawning the worker, and share nothing but bytes
  (B11 original + tail).
- _Renders can't be cancelled:_ keep tiles small, prioritize visible tiles, drop stale results,
  and document the limitation against "every job cancellable" (CLAUDE.md rule 2).

## S4 — PDF Oxide WASM: size, Markdown/HTML/table quality, WASM API availability

**Goal.** Decide whether `pdf-oxide-wasm` (npm, v0.3.77, `MIT OR Apache-2.0`) can serve as the
extraction engine for text, Markdown, HTML, tables and images (§7.6, §7.7) inside the Work
worker.

**Method.**

1. Install the package in `spikes/s4-oxide/` and run `npm run licenses`.
2. List the functions the WASM build actually exports and compare them with the native crate's
   features: text, Markdown, HTML, tables, images, per-page and streaming use.
3. Load it in a module worker with no network access. Record:
   - WASM size (raw, gzip, brotli);
   - initialization time;
   - peak memory.
4. Run it on:
   - the FAR (throughput in pages per second for text and Markdown);
   - a sample of public test PDFs;
   - a public **pipe dimension chart** style table fixture (§7.7). The source must be confirmed
     public by the owner, and it is fetched by script, never committed.
5. Score quality with a simple rubric: reading order, headings, lists, and table cell accuracy on
   three tables checked by hand.
6. Compare against PDFium text extraction (`FPDFText_*`) as a baseline.

**Success criteria.**

- The WASM build exposes text, Markdown, HTML and table extraction (images optional, because
  PDFium can do those).
- It runs entirely in a worker with no network access.
- The compressed WASM size fits the 60 MB install budget (§9). Proposed target: 10 MB or less
  after brotli.
- FAR text/Markdown extraction completes and is cancellable between pages. Throughput is reported.
- Table cell accuracy is 90 % or better on the lattice-style fixture. Stream-style accuracy is
  reported.

**If it fails.**

- _APIs are missing from the WASM build:_ build our own `wasm-bindgen` wrapper around the
  permissive Rust crate, which needs an ADR and CI build steps. Or use PDFium text extraction
  plus our own Markdown and table heuristics.
- _The package is too large:_ lazy-load it in the background after core precache (D-17). It is
  already planned as non-core.
- _Quality is poor:_ keep the Beta labels, lean on Review & Extract with an editable grid and
  templates, and treat Oxide as one candidate among lattice and stream (§7.7).

## S5 — Search in the Work worker on a ~2,000-page document while scrolling

**Goal.** Confirm the §6 targets: first hits in under 1 s, a full 2,000-page search in under 15 s,
and **no main-thread task over 100 ms**, with search running in the Work worker while the user
scrolls.

**Method.**

1. Build a spike app. The Render worker drives EmbedPDF's viewport, scroll and tiling plugins.
   The Work worker extracts text per page with PDFium (`FPDFText_*`) and builds the index lazily
   in viewport order, then the rest.
2. Search runs on Enter only (D-08). Results stream back in batches no more often than about
   every 50 ms, and a new search cancels the previous one through an AbortSignal message.
3. Check where EmbedPDF's own `plugin-search` runs. If it runs in the Render engine, it violates
   D-10, so we don't use it for Advanced Search.
4. Write a Playwright scenario on the **FAR** (public, about 2,000 pages): open, start
   auto-scrolling, type a query and press Enter, keep scrolling, then run a second query that
   cancels the first. Record `longtask` entries, time to first hit, time to completion, and
   cancellation latency.
5. Run it in CI (informative numbers). The owner runs it on the reference-class machine.

**Success criteria.**

- Zero main-thread long tasks over 100 ms throughout the scenario.
- First hits under 1 s and completion under 15 s on the reference-class machine.
- A new search stops the old one within 100 ms, and no stale results appear.
- Scrolling stays smooth during search, with no blank tile flashes attributable to search.

**If it fails.**

- _Main-thread jank from results:_ coarser batches, a virtualized results list, and deferring
  highlight rendering to visible pages only.
- _Extraction too slow:_ cache the text index locally per document fingerprint (IndexedDB, never
  sent anywhere), prioritize visible pages first, and consider a second Work worker for indexing
  only.
- _PDFium text extraction too slow compared with PDF Oxide:_ use whichever S4 shows is faster.

## S6 — Fluent Color icon coverage for the ribbon; list of custom icons required

**Goal.** Map every Rev 0 ribbon command (the §8 tabs File, Home, View, Comment, Measure,
Organize, Convert, Protect and Help) to a Fluent UI System Icon in the **Color** style (D-20),
and list the icons we must draw ourselves.

**Method.**

1. Build the command inventory from §5–§8, using the reference screenshots for layout only.
2. Search `@fluentui/react-icons` (v2.0.341, MIT) for `*Color` exports at 16, 20, 24, 32 and
   48 px, plus Regular and Filled fallbacks.
3. Produce `docs/plan/S6-icon-map.md`, listing for each command: the Fluent icon name and sizes,
   or "custom needed".
4. Measure the tree-shaken bundle cost of the chosen set.

**Success criteria.**

- Every Rev 0 ribbon command has an icon entry.
- The custom list includes at least the icons named in §8 (cloud, calibrate, scale viewport, CRS
  export, express extract), plus any others found.
- Icons tree-shake, and the bundle delta is reported.
- No PDF-XChange artwork is referenced or copied (CLAUDE.md rule 15).

**If it fails.**

- _Color coverage is too thin:_ use Regular or Filled variants tinted with design tokens for the
  missing ones, or draw more custom Color-style icons in `src/ui/icons`. The owner picks the
  visual consistency trade-off.
- _Bundle cost is too high:_ import icons by path, or generate an SVG sprite at build time.

## S7 — Vector geometry extraction speed for snapping on a dense P&ID

**Goal.** Measure how quickly the Work worker can extract vector path geometry for a page region
and answer snap queries (endpoint, midpoint, intersection, nearest-on-segment) interactively
(§7.4).

**Method.**

1. Walk page objects with PDFium:
   - `FPDFPage_CountObjects` and `FPDFPage_GetObject`;
   - path objects via `FPDFPath_CountSegments`, `FPDFPath_GetPathSegment` and
     `FPDFPathSegment_GetPoint`;
   - `FPDFPageObj_GetMatrix`, recursing into form XObjects.
2. Check whether EmbedPDF exposes these. Otherwise call PDFium directly (B14).
3. Flatten the geometry into transferable typed arrays and build a static spatial index. Use a
   permissive library such as `flatbush` (ISC) or our own grid.
4. Answer snap queries through RPC on pointer move, coalesced to one request per animation frame.
5. Measure per page: segment count, extraction time, index build time, memory, and query
   round-trip latency.
6. Inputs: public drawings where available (sources to be proposed and confirmed by the owner),
   plus the owner's **local dense P&ID** (B15).

**Success criteria.**

- The snap query round trip (main → worker → main) takes 16 ms or less at the 95th percentile.
- Geometry extraction runs in the background without delaying the Render worker's tiles, and the
  numbers are reported for the owner's P&ID (relaxed targets, B9).
- Results are correct against a self-made test sheet with known endpoints and intersections
  (unit-tested geometry, TDD).

**If it fails.**

- _Extraction too slow for whole pages:_ extract only the visible region, or tiles around the
  cursor, and cache per page and region.
- _Too many segments:_ drop segments below a pixel threshold at the current zoom, or enable
  snapping only above a zoom threshold.
- _PDFium path API not reachable:_ derive geometry from PDF Oxide, if S4 shows it exposes
  vectors, or parse content streams in the worker. That needs an ADR.

## S8 — CSP + Cloudflare analytics + WASM coexistence

**Scope updated by ADR-001 B1.** Analytics is Cloudflare's **server-side** request counts only,
with **no beacon script**, so the §10.1 CSP stays unchanged. S8 therefore proves that the real
CSP, WASM, module workers, the service worker and the EmbedPDF engine coexist on Cloudflare Pages
with zero third-party requests.

**Method.**

1. Build a minimal Vite build of the S3 spike with `public/_headers` carrying the §10.1 CSP
   verbatim.
2. Serve it with `wrangler pages dev` locally, and deploy it to a Cloudflare Pages preview on
   the owner's account.
3. Load the EmbedPDF engine in a module worker (`worker-src 'self' blob:`), with WASM compiled
   under `'wasm-unsafe-eval'` and `pdfium.wasm` self-hosted.
4. Open a PDF whose fonts need CJK fallback, and confirm that no request goes to jsDelivr.
   Font fallback must be disabled or pointed at local files.
5. Register a service worker with a vite-plugin-pwa precache of the core, then reload offline.
6. Write a Playwright check that:
   - collects `securitypolicyviolation` events and console CSP errors;
   - asserts zero cross-origin requests;
   - verifies the offline reload.
7. Confirm in the Cloudflare dashboard that Web Analytics' automatic JS injection is **off** for
   the project, and that server-side request analytics still reports page counts.
8. Repeat the smoke check in Firefox.

**Success criteria.**

- Zero CSP violations with the §10.1 policy unchanged.
- Zero third-party requests, including during font fallback.
- An offline reload after the first visit works in Chrome and Edge. Firefox is noted.
- No analytics script is injected into responses, and server-side counts are visible to the owner.

**If it fails.**

- _EmbedPDF needs `eval`, `blob:` scripts or other CSP relaxations:_ make the smallest possible
  CSP change, recorded in an ADR, or patch the loader configuration.
- _Font fallback can't be disabled:_ bundle the required `@embedpdf/fonts-*` locally (needs the
  OFL-1.1 decision) or supply our own font config.
- _Cloudflare injects a beacon anyway:_ disable it in project settings. As a last resort, the
  Pages Function strips it and we document that.
